# local-agent --- план разработки и контроля

**Назначение:** этот файл --- единственный контрольный документ проекта.
Пользователь ведёт в нём статусы, результаты проверок и решения о
приёмке. При переходе в новый чат файл передаётся целиком, чтобы
продолжение работы не зависело от памяти предыдущего чата.

**Проект:** `local-agent`\
**Репозиторий:** https://github.com/ecokot/local-agent\
**Основная ветка:** `main`\
**Среда:** Windows 11, Python 3.12+, `uv`, PowerShell, PyCharm

## 1. Как пользоваться документом

### Статусы

Использовать один из статусов:

-   `[ ]` --- не начато;
-   `[~]` --- в работе;
-   `[x]` --- выполнено и принято;
-   `[!]` --- есть проблема или блокер;
-   `[-]` --- отложено осознанным решением.

Отмечать этап как `[x]` можно только после выполнения его критериев
приёмки. Сам факт наличия кода не означает, что этап завершён.

### Правила ведения

1.  Работать только над одним этапом одновременно.
2.  Перед началом этапа сверить рабочую копию с Git и изучить актуальный
    код.
3.  Не менять файлы, пока не изучены их текущие версии и тесты.
4.  Делать небольшие, ограниченные изменения.
5.  Не переписывать работающий код без конкретной причины.
6.  После логически законченного изменения запускать подходящие
    проверки. Полный набор тестов запускать на контрольных точках и при
    приёмке этапа, а не механически после каждой мелочи.
7.  Не объявлять проверку пройденной, если команда не запускалась.
8.  Не переходить дальше, пока текущий этап не принят.
9.  После приёмки этапа проверить diff, сделать commit и push.
10. При обнаружении уже реализованного функционала не создавать его
    заново: сначала проверить реализацию по критериям этапа.

### Обязательный отчёт при завершении каждого этапа

-   Что сделано.
-   Какие файлы изменены.
-   Какие технические решения приняты и почему.
-   Какие тесты добавлены или изменены.
-   Результат `uv run ruff check .`.
-   Результат `uv run pytest -v`.
-   Результат `git diff --check`.
-   Известные ограничения и нерешённые вопросы.
-   Commit hash и результат push.
-   Решение: этап принят или не принят.

## 2. Цель проекта

Создать локального автономного Python-агента для Windows, который
способен:

1.  Получить задачу пользователя.
2.  Исследовать существующий проект или подготовить новый.
3.  Изучить необходимые файлы и структуру.
4.  Сформировать план и дождаться его одобрения.
5.  Выполнить разрешённые действия через Python-инструменты.
6.  Запустить проверки и проанализировать результаты.
7.  Исправить обнаруженные ошибки в пределах задачи.
8.  Подтвердить результат объективными проверками.
9.  Сохранить состояние и историю так, чтобы корректно восстановиться
    после перезапуска.

### Архитектурные принципы

-   Модель анализирует, планирует и предлагает изменения.
-   Python управляет состоянием, файлами, инструментами, разрешениями,
    выполнением и проверками.
-   Модель не исполняет инструменты напрямую и не обходит
    Python-оркестрацию.
-   Контекст для модели формируется приложением явно и контролируемо.
-   SQLite --- источник истины для состояния и подтверждённых данных.
-   JSONL --- восстанавливаемое представление истории событий, если это
    подтверждено реализацией ExecutionRecorder.
-   Не добавлять менеджеры, уровни абстракции и проверки без конкретной
    необходимости.
-   Сначала получить минимальный работающий и проверяемый процесс, затем
    расширять возможности.

## 3. Текущее известное состояние проекта

Этот раздел фиксирует известную отправную точку. Он не заменяет
повторную проверку репозитория на этапе 0.

### Подтверждено в предыдущей работе

-   Базовая структура Python-проекта создана.
-   Используются `uv`, Ruff и pytest.
-   `StateManager` переведён на SQLite; реализацию и критерии
    восстановления нужно повторно сверить.
-   `ApprovalManager` реализован с хранением подтверждений в SQLite.
-   `ExecutionRecorder` реализован; надёжность SQLite/JSONL ещё не
    принята по отдельному контрольному этапу.
-   Есть модели задач, планов, подтверждений и результатов агентов.
-   Есть протоколы `Planner`, `Executor`, `Reviewer` и stub-реализации.
-   Есть `Orchestrator` с подготовкой плана, одобрением, выполнением,
    проверкой и отклонением плана.
-   Есть базовый `UserInterface` и консольная точка входа.
-   Консольный smoke test проверил одобрение плана и отклонение плана.
-   StubExecutor имитирует выполнение и **не создаёт файлы на диске**.
-   Последний известный полный прогон: `115 passed`; Ruff:
    `All checks passed!`. Эти результаты относятся к предыдущему
    состоянию кода и должны быть повторно подтверждены на этапе 0.
-   Последний известный коммит с CLI отправлен в `origin/main`. Точный
    hash и чистоту рабочей копии проверить командой Git.

### Важное правило

Некоторые компоненты реализованы раньше их места в плане. Их не нужно
автоматически удалять или переписывать. До соответствующего этапа они
считаются предварительной реализацией. На своём этапе каждый компонент
проверяется по критериям и либо принимается, либо дорабатывается.

## Этап 5. Разрешения и подтверждения пользователя

**Статус:**

- [x] Принят с ограничением

**Ограничение**
Политика разрешений отдельных действий не реализована и не считается принятой. Это осознанно перенесено на этап 6.

Политика разрешений и граница исполнения
- Реализовать централизованную Python-политику определения разрешённых действий.
- Безопасные действия выполнять без запроса подтверждения.
- Для рискованных действий требовать подтверждение пользователя.
- Проверять разрешение непосредственно перед исполнением каждого действия.
- Проверка должна выполняться Python-кодом, а не моделью.
- Исполнитель не должен иметь возможности обойти проверку разрешений.
- Подтверждение должно относиться к конкретному действию и его параметрам.
- Отменённое или не подтверждённое действие не должно запускаться.
- Покрыть эти сценарии тестами.


**Цель:** обеспечить контролируемое выполнение потенциально опасных
действий.

### Требования

-   Различать безопасные действия и действия, требующие подтверждения.
-   Привязывать подтверждение к конкретному действию и его параметрам.
-   Сохранять подтверждения в SQLite.
-   Восстанавливать ожидающее подтверждения действие после перезапуска.
-   Не считать изменённые параметры подтверждёнными.
-   Не удалять ожидающую задачу по таймауту.
-   Поддерживать окончательную отмену.
-   Разделять одобрение общего плана и подтверждение конкретного
    рискованного действия, если оба уровня нужны.

### Уже принятое продуктовое поведение

-   Подтверждение привязано к действию и его параметрам.
-   Если параметры изменились, требуется новое подтверждение.
-   После перезапуска неизменённое подтверждённое действие может
    продолжить выполнение.
-   Если пользователь не ответил, задача остаётся в ожидании без
    автоматического таймаута.
-   Отмена должна исключать последующее выполнение отменённого действия.

### Критерии приёмки

-   Подтверждённое неизменённое действие может быть восстановлено после
    перезапуска.
-   Изменённые параметры требуют нового подтверждения.
-   Отменённое действие не запускается.
-   Статусы задачи и подтверждения согласованы.
-   Тесты покрывают сценарии перезапуска и изменения параметров.

## Снимок структуры проекта

Выполнить из корневой папки проекта в PowerShell.

Скрипт создаёт файл `PROJECT_STRUCTURE.txt`, содержащий:
- текущий этап разработки;
- короткий SHA текущего Git-коммита;
- дату и время создания снимка;
- актуальное дерево файлов и каталогов проекта.

Из дерева исключаются каталоги `.venv`, `.git`, `.idea`, `.pytest_cache`, `.ruff_cache`, `__pycache__` на всех уровнях вложенности.

### Команда

```powershell
$stage = "Этап 5"
$root = (Get-Location).Path
$commit = git rev-parse --short HEAD

if ($LASTEXITCODE -ne 0) {
    throw "Не удалось получить Git-коммит. Проверьте, что текущая папка является Git-репозиторием."
}

$exclude = @(
    ".venv",
    ".git",
    ".idea",
    ".pytest_cache",
    ".ruff_cache",
    "__pycache__"
)

function Get-ProjectTree {
    param(
        [string]$Path,
        [string]$Prefix = ""
    )

    $items = @(
        Get-ChildItem -LiteralPath $Path -Force |
        Where-Object {
            -not ($_.PSIsContainer -and $_.Name -in $exclude)
        } |
        Sort-Object @{ Expression = { -not $_.PSIsContainer } }, Name
    )

    for ($i = 0; $i -lt $items.Count; $i++) {
        $item = $items[$i]
        $last = $i -eq ($items.Count - 1)

        $branch = if ($last) { "\--- " } else { "+--- " }

        "$Prefix$branch$($item.Name)"

        if ($item.PSIsContainer) {
            $nextPrefix = $Prefix + $(if ($last) { "    " } else { "|   " })
            Get-ProjectTree -Path $item.FullName -Prefix $nextPrefix
        }
    }
}

$lines = @(
    "ЭТАП: $stage"
    "КОММИТ: $commit"
    "ДАТА: $(Get-Date -Format 'yyyy-MM-dd HH:mm:ss')"
    ""
    "СТРУКТУРА ПРОЕКТА"
    (Split-Path $root -Leaf)
)

$lines += @(Get-ProjectTree -Path $root)

$output = Join-Path $root "PROJECT_STRUCTURE.txt"
$lines | Set-Content -LiteralPath $output -Encoding UTF8

Write-Host "Снимок структуры проекта создан: $output"
```

# local-agent

Локальный Python-проект автономного агента для исследования и изменения
программных проектов. Цель проекта — не просто генерировать код, а
проводить задачу через управляемый цикл: исследование, планирование,
одобрение пользователя, выполнение, проверки и подтверждение результата.

Проект находится в активной разработке. Полноценный автономный цикл
пока не собран: текущая работа ведётся над интеграцией Orchestrator
с уже реализованными компонентами.

## Основные принципы

- **Python управляет выполнением.** Состояние задач, файлы, разрешения,
  подтверждения, запуск инструментов и проверки находятся под контролем
  приложения.
- **Модель предлагает решения.** Модель не должна напрямую запускать
  локальные инструменты или обходить Python-контур.
- **План одобряет пользователь.** Выполнение плана не должно начинаться
  до явного одобрения.
- **Действия проверяемы.** Результат должен подтверждаться реальными
  результатами инструментов и проверок, а не только сообщением модели.
- **Локальная работа.** Проект рассчитан на Windows 11 и локальную
  инфраструктуру; обязательная зависимость от облачного API не является
  целью проекта.

## Текущее состояние

По состоянию на 25.11.2026 приняты этапы 0–6, все подэтапы этапов 7 и 8, а также подэтапы 9.А и 9.Б. На этапе 9.Б реализован самостоятельный read-only GitTool и Windows runner. Следующий подэтап — 9.В: интеграция GitTool с существующей цепочкой ToolExecutor и ToolExecutorAdapter.

- Реализованы модели задач, планов, результатов агентов и подтверждений.
- Реализованы SQLite-компоненты управления состоянием задач и
  подтверждениями.
- Реализованы запись истории выполнения и отдельный механизм проверки
  и восстановления истории.
- Реализованы Orchestrator, консольный интерфейс и протоколы Planner,
  Executor и Reviewer; сейчас они используют тестовые заглушки.
- Реализованы ModelClient и ModelRouter для работы с OpenAI-compatible API.
- Реализованы Workspace, ToolExecutor и инструменты для просмотра
  структуры, чтения, создания и изменения файлов, получения diff,
  запуска команд и тестов.
- Команды выполняются через самостоятельный Docker-based ExecutionBackend
  с ограничениями контейнера и временной Workspace.

**Важное ограничение:** исполнительные инструменты и Docker Backend
реализованы и протестированы, но пока не подключены к Orchestrator
в единый автономный цикл. ModelClient, ModelRouter и ContextManager
также ещё не интегрированы в полный цикл Orchestrator. Текущий CLI
использует StubPlanner, StubExecutor и StubReviewer и не является
полноценным автономным агентом.

Актуальные статусы, критерии и решения о приёмке ведутся исключительно в [plan.MD](plan.MD). Исторические результаты и доказательства завершённых работ приведены в [docs/DEVELOPMENT_HISTORY.md](docs/DEVELOPMENT_HISTORY.md).

## Архитектура

Основные компоненты:

| Компонент | Ответственность |
|---|---|
| `StateManager` | Состояние задач в SQLite |
| `ApprovalManager` | Запросы, решения и хранение подтверждений |
| `Orchestrator` | Координация планирования, одобрения, выполнения и ревью |
| `ContextManager` | Управление сообщениями контекста |
| `ModelClient` | Вызов модели через OpenAI-compatible API |
| `ModelRouter` | Выбор модели по роли |
| `ExecutionRecorder` | Запись истории выполнений и событий |
| `RecoveryManager` | Проверка и восстановление истории выполнений |
| `Workspace` | Ограничение файловой рабочей области |
| `ToolExecutor` | Проверка разрешений и диспетчеризация инструментов |
| `ExecutionBackend` | Запуск команд в изолированных Docker-контейнерах |

Подробные публичные контракты, связи модулей и известные ограничения
описаны в [MODULE_CONTRACTS.md](MODULE_CONTRACTS.md).

## Технологии

- Python 3.12+
- [uv](https://docs.astral.sh/uv/) — управление окружением и зависимостями
- Pydantic — модели и валидация данных
- OpenAI-compatible API — интерфейс взаимодействия с языковыми моделями
- SQLite — постоянное состояние задач и подтверждений
- Docker — изолированное выполнение команд
- pytest — автоматические тесты
- Ruff — проверка качества кода

## Требования

Для разработки:

- Windows 11;
- Python 3.12 или новее;
- uv.

Для выполнения команд через Docker Backend и запуска Docker integration tests:

- Docker Desktop с Linux Containers;
- подготовленный локальный образ, указанный в настройках ExecutionBackend
  (по умолчанию `local-agent-python-test:3.12`).

Базовый CLI со stub-агентами не требует запуска Docker.

## Установка

Клонировать репозиторий и перейти в каталог проекта:

```powershell
git clone https://github.com/ecokot/local-agent.git
cd local-agent
uv sync
```

## Запуск

Запустить консольный интерфейс:

```powershell
uv run local-agent
```

На текущем этапе CLI использует тестовые заглушки Planner, Executor
и Reviewer. Запуск интерфейса демонстрирует базовый сценарий подготовки
плана, его одобрения или отклонения, но не запускает полноценный цикл
автономной разработки через реальные модели и инструменты.

## Проверки

Запустить полный набор тестов:

```powershell
uv run pytest -v
```

Проверить код Ruff:

```powershell
uv run ruff check .
```

Перед коммитом проверить diff:

```powershell
git diff --check
```

Docker integration tests требуют работающего Docker Engine и локально
доступного тестового образа. Подробности настройки и ограничений
исполнения описаны в [docs/EXECUTION_BACKEND.md](docs/EXECUTION_BACKEND.md)
и [docs/EXECUTION_ISOLATION_RESEARCH.md](docs/EXECUTION_ISOLATION_RESEARCH.md).

## Организация работы AI-ролей

Разработка сопровождается двумя отдельными навыками:
- **Project Planner** определяет цель, формирует ограниченную задачу, координирует работу и независимо проверяет результат.
- **Project Developer** изучает код, реализует согласованную задачу, запускает проверки и готовит фактический отчёт.

Навыки задают поведение ролей, но не заменяют проектный план, технические контракты, постановку конкретной задачи или историю разработки. Совместимый AI-клиент должен загрузить соответствующий `SKILL.md`; наличие файлов в репозитории само по себе не активирует навыки автоматически.

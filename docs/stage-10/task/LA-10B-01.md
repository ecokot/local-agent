## 2. Context

Stage 10.A is accepted and merged. Startup recovery restores task state and classifies unresolved tasks, but it does not restore the in-memory execution progress held by `ToolExecutorAdapter`.

Current relevant behavior:

- `ToolExecutorAdapter` stores the approved plan, next step, completed step results, and reusable completed-step signatures in process memory.
- `Orchestrator.execute_approved_plan()` receives an approved plan approval and delegates execution to the configured Executor.
- `ApprovalManager` persists plan/action approvals in SQLite and binds them to canonical parameter hashes.
- `ToolExecutor` records individual tool executions through `ExecutionRecorder`; the recorder stores execution status and event data in SQLite and projects events to JSONL.
- `RecoveryManager` runs at startup but deliberately does not invoke agents or tools.

The relevant implementation and contracts are in:

- `src/local_agent/agents/tool_executor_adapter.py`
- `src/local_agent/orchestrator.py`
- `src/local_agent/state_manager.py`
- `src/local_agent/approval_manager.py`
- `src/local_agent/execution/tool_executor.py`
- `src/local_agent/execution/recorder.py`
- `MODULE_CONTRACTS.md`

## 3. Goal and expected result

Persist enough execution-plan progress in SQLite so a newly constructed application process can restore a task's confirmed progress and, when explicitly asked to resume through the existing approved-plan flow, continue from the first step that is proven not to have completed.

The persisted progress must be bound to the exact approved plan and its step parameters. Completed steps must not be executed again when their completion is durably recorded. The implementation must fail closed when it cannot establish whether an interrupted step completed.

Startup recovery must remain non-executing: it may load and classify progress, but must not automatically invoke Planner, Executor, Reviewer, ToolExecutorAdapter, or tools.

## 4. Scope

### 4.1 Included

- Add durable SQLite-backed execution progress for each task and approved plan revision.
- Persist the approved plan snapshot, approval identity/revision, canonical plan identity, next step, per-step state, completed results, and associated tool execution IDs where available.
- Persist a step as in-progress before dispatching its tool.
- Persist a completed step's result before advancing to the next step.
- Persist the waiting-for-action-approval state and pending approval ID for the current step.
- Restore progress when a new adapter/orchestrator instance is created against the same database.
- Resume through the existing approved-plan execution entry point after the relevant approval is approved.
- Preserve already completed steps across an approved plan revision only when they form an identical leading prefix by action and canonical parameters, consistent with current adapter behavior.
- Retain durable progress after runtime progress is cleared or a task reaches a terminal state; runtime cleanup must not erase the recovery record.
- Add focused unit and restart-style integration tests using a temporary SQLite database and fresh component instances.

### 4.2 Excluded

- Universal exactly-once execution or automatic retries of arbitrary external effects.
- Automatically repeating a step whose persisted state says it was in progress when the process stopped, or whose completion cannot be proven.
- Inspecting/reconciling arbitrary external systems to determine whether an uncertain action took effect.
- General idempotency keys, tool-specific deduplication, or the broader action-safety work assigned to stage 10.C.
- Automatic execution/resume during application startup.
- CLI work (stage 11), real model-backed agents, coder/reviewer loops, distributed transactions, and generic retry/backoff.
- Rewriting `ExecutionRecorder` or changing its JSONL projection unless a concrete compatibility issue makes a minimal change necessary.
- Changes to `plan.MD`.

## 5. Requirements

- **REQ-01 — Durable plan identity:** Persist the approved plan snapshot and bind progress to the task, plan approval identity/revision, and a deterministic canonical representation of the plan. A different plan must never silently inherit progress for changed steps.
- **REQ-02 — Durable step checkpoints:** Persist the ordered step states and confirmed results in SQLite. A step must be marked in-progress before its tool is dispatched. A successful result, including its step index, action, parameters, and execution ID when available, must be durably stored before the next step is dispatched.
- **REQ-03 — Restart restoration:** A fresh `ToolExecutorAdapter`/execution flow using the same database must restore completed step results and the next step without relying on process memory.
- **REQ-04 — Approval pause/resume:** When a step waits for approval, persist its identity and pending approval ID. After that same action is approved, resuming the same approved plan must continue at that step without rerunning earlier completed steps and without bypassing `ApprovalManager`.
- **REQ-05 — Plan revision safety:** If an approved plan changes while execution is suspended, do not replace the suspended plan or execute the changed plan against its progress. For a new approved revision after the prior plan completed, reuse only the identical completed leading prefix (same action and canonical parameters); discard progress for the changed suffix. A changed step must execute only under its own approved plan/action parameters.
- **REQ-06 — Uncertain in-progress step:** If restart finds a step persisted as in-progress without a durable completion result, do not dispatch that step again and do not mark it successful. Return a clear unresolved/recovery error or equivalent non-terminal classification for explicit handling by the later 10.C flow. Earlier durably completed steps remain available.
- **REQ-07 — Durable retention:** Clearing in-memory execution state or transitioning a task to a terminal state must not delete its persisted progress/results. Existing terminal task and approval semantics remain unchanged.
- **REQ-08 — Startup boundary:** Recovery remains observational and non-executing. Restoring progress must not automatically resume a task or call any agent/tool during startup.
- **REQ-09 — Compatibility:** Preserve existing plan approval, per-action approval, task-state, verification, ExecutionRecorder, and Git stage-receipt behavior. Do not weaken approval hash checks or bypass the existing ToolExecutor approval path.
- **REQ-10 — Diagnostics and integrity:** Missing, malformed, contradictory, or plan-mismatched progress must be reported explicitly. Do not silently repair or reinterpret persisted progress. Repeated restoration of unchanged data must be idempotent.

## 6. Fixed decisions and delegated implementation choices

### 6.1 Fixed decisions

- SQLite remains the source of truth for durable state.
- Progress is task-scoped and bound to the approved plan/revision and exact step parameters.
- A step is considered completed only when its completion result has been durably persisted.
- An interrupted in-progress step is unresolved and must not be automatically repeated in 10.B.
- Startup recovery must not execute work.
- Existing approval decisions and parameter-hash enforcement remain authoritative.
- No changes to `plan.MD`.

### 6.2 Delegated decisions

Developer may choose the minimal persistence API, schema/migration approach, transaction boundaries, and whether the existing StateManager or a narrowly scoped existing component owns the progress records. Prefer the smallest design that fits current SQLite ownership and module contracts. Do not add a new manager or abstraction unless the existing components cannot reasonably own the responsibility.

Developer may define internal step-state names and typed error/result models, provided all requirements and acceptance criteria remain observable and tested.

## 10. Acceptance criteria

- **AC-01 (REQ-01):** The approved plan snapshot and canonical identity are persisted and validated on resume; a mismatched plan cannot silently reuse progress.
- **AC-02 (REQ-02):** Step start and completion checkpoints are durable and ordered; no next step is dispatched before the previous successful result is persisted.
- **AC-03 (REQ-03):** A fresh process/component instance restores the same confirmed completed results and next-step position from SQLite.
- **AC-04 (REQ-04):** A task paused for action approval resumes after approval at the pending step, with prior completed steps skipped and approval enforcement intact.
- **AC-05 (REQ-05):** Suspended plan replacement is rejected; a new revision after completed execution reuses only an identical completed leading prefix.
- **AC-06 (REQ-06):** An in-progress step without a completion checkpoint is surfaced as unresolved and is never automatically dispatched again or reported successful.
- **AC-07 (REQ-07):** Runtime cleanup and terminal task transitions retain durable progress records.
- **AC-08 (REQ-08):** Startup recovery restores/classifies progress without invoking agents, adapters, executors, or tools.
- **AC-09 (REQ-09):** Existing approval, task lifecycle, verification, recorder, and Git receipt regression tests continue to pass.
- **AC-10 (REQ-10):** Corrupt or contradictory progress produces explicit diagnostics; repeated recovery of valid unchanged progress is idempotent.

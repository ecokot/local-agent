## 2. Контекст

Подэтап 10.A должен подключить существующий механизм восстановления к запуску приложения. Задача ограничена восстановлением сохранённого состояния и безопасной классификацией незавершённых задач. Сохранение позиции и результатов шагов ToolExecutorAdapter относится к 10.B; автоматический повтор или продолжение внешних действий — к 10.C и не входит в эту задачу.

Факты baseline `1b4d709d0f391a847727c34abf2b50a841436463`:

- `src/local_agent/recovery_manager.py` содержит `RecoveryManager.recover()`, который проверяет события Execution, восстанавливает RUNNING-задачу в SUCCEEDED при доказанно успешном последнем Execution и проверяет согласованность ожидающих подтверждений.
- Для RUNNING-задачи без Execution, с последним FAILED или RUNNING Execution текущий RecoveryManager оставляет статус RUNNING. Причина такого решения — отсутствие достаточных доказательств окончательного исхода.
- Для WAITING_FOR_APPROVAL проверяется наличие хотя бы одного PENDING approval; противоречивые комбинации приводят к `RecoveryError`.
- `RecoveryManager` пока не вызывается автоматически при запуске `UserInterface` или `Orchestrator`.
- Точка входа приложения — `main()` в `src/local_agent/__init__.py`. Она создаёт StateManager и ApprovalManager, затем Orchestrator и UserInterface. ExecutionRecorder сейчас создаётся внутри исполнительного контура; для восстановления на старте ему потребуется открыть то же SQLite-хранилище.
- StateManager и ApprovalManager используют одно SQLite connection. ExecutionRecorder открывает собственное соединение к указанному файлу базы данных.
- `ExecutionRecorder` уже восстанавливает отложенные trace-файлы при инициализации. Его внутреннюю реализацию не переписывать без доказанного дефекта.

## 3. Цель и ожидаемый результат

При каждом штатном запуске приложения сохранённое состояние проверяется до запуска пользовательского интерфейса. Подтверждённо завершённые задачи восстанавливаются в терминальный успешный статус; ожидающие подтверждения остаются ожидающими; состояния, исход которых нельзя доказать, явно перечисляются как требующие внимания. Противоречивые данные не исправляются молча и блокируют запуск интерфейса с диагностикой.

Восстановление не запускает инструменты, не повторяет действия и не продолжает незавершённые планы.

## 4. Объём работ

Разрешено и требуется:

- Подключить существующий RecoveryManager в composition root приложения `main()` в `src/local_agent/__init__.py`.
- При запуске создать ExecutionRecorder для того же файла SQLite, который использует StateManager и ApprovalManager; передать его существующему RecoveryManager.
- Выполнять восстановление ровно один раз за запуск приложения и до вызова `UserInterface.run()`.
- Обеспечить корректное закрытие ExecutionRecorder при штатном завершении приложения.
- Расширить результат `RecoveryManager.recover()` так, чтобы вызывающий код мог различать:
  - задачи, которые были автоматически восстановлены в SUCCEEDED;
  - задачи, корректно ожидающие пользовательского подтверждения;
  - задачи, которые нельзя безопасно классифицировать как завершённые и которые требуют внимания.
- Для CREATED без pending approval и RUNNING без Execution, с последним FAILED либо RUNNING Execution возвращать явную диагностику неопределённого состояния. Не переводить такие задачи автоматически в SUCCEEDED, FAILED или CANCELLED.
- Сохранить текущие проверки согласованности истории Execution и approvals. При противоречивых данных поднимать RecoveryError с идентификатором задачи и понятной причиной.
- Проверить сценарии нескольких задач: восстановление одной задачи не должно приводить к ошибочному изменению статуса другой.
- Обновить раздел RecoveryManager и описание startup wiring в `MODULE_CONTRACTS.md`, если публичный результат восстановления или фактические связи компонентов изменятся.
- Добавить/обновить автоматические тесты для RecoveryManager и запуска приложения.
- Подготовить отчёт `docs/stage-10/report/LA-10A-01.md` по полному `docs/templates/REPORT_TEMPLATE.md`.

Не входит в задачу:

- Сохранение и восстановление позиции, текущего шага и результатов `ToolExecutorAdapter` — подэтап 10.B.
- Повторный запуск, автоматическое продолжение или проверка фактического результата неопределённого внешнего действия — подэтап 10.C.
- Изменение алгоритмов выполнения ToolExecutor, GitTool или других инструментов.
- Изменение правил одобрения, хеширования параметров, отмены и отказа в ApprovalManager.
- Изменение схемы SQLite без доказанной необходимости и отдельного обоснования.
- Переписывание ExecutionRecorder или JSONL/trace recovery без обнаруженного дефекта.
- Полноценный CLI для просмотра/возобновления задач — этап 11.
- Реальные Planner/Coder/Reviewer, новые зависимости, новые менеджеры и несвязанный рефакторинг.
- Изменение `plan.MD`.

## 5. Требования

- **REQ-01:** При штатном запуске `main()` создаёт RecoveryManager на основе существующих StateManager, ApprovalManager и ExecutionRecorder, причём все компоненты используют один и тот же файл SQLite.
- **REQ-02:** `RecoveryManager.recover()` вызывается один раз при запуске и до `UserInterface.run()`. Если восстановление завершается RecoveryError, пользовательский интерфейс не запускается, а ошибка содержит идентификатор проблемной задачи и диагностическую причину.
- **REQ-03:** Задача RUNNING с валидной историей, где последний Execution имеет статус SUCCEEDED и согласованное терминальное событие, переводится в TaskStatus.SUCCEEDED. Задачи в терминальных статусах не изменяются.
- **REQ-04:** Задачи WAITING_FOR_APPROVAL с одним или несколькими PENDING approvals остаются в WAITING_FOR_APPROVAL; сами записи и идентификаторы approvals сохраняются без пересоздания. WAITING_FOR_APPROVAL без PENDING approval, RUNNING с PENDING approval, а также pending approval у CREATED или терминальной задачи считаются противоречивым состоянием и приводят к RecoveryError.
- **REQ-05:** CREATED без pending approval, RUNNING без Execution, RUNNING с последним Execution в статусе FAILED и RUNNING с последним Execution в статусе RUNNING классифицируются как unresolved. Для них возвращается task_id, исходный TaskStatus и краткая причина; их статус не меняется. Никакое из этих состояний не объявляется успешным или окончательно неуспешным без доказательств.
- **REQ-06:** Результат recover() предоставляет типизированные коллекции идентификаторов восстановленных задач, задач с ожидающими подтверждениями и unresolved-задач с диагностикой. Допускается эквивалентный минимальный типизированный контракт, если он предоставляет все эти данные без потери информации.
- **REQ-07:** Повторный вызов recover() безопасен: уже восстановленные терминальные задачи не изменяются повторно, pending approvals не дублируются, новые записи истории не создаются.
- **REQ-08:** Восстановление не вызывает Planner, Executor, ToolExecutor, инструменты или повторное выполнение действий. Unresolved-задачи только диагностируются.
- **REQ-09:** Проверки последовательности и типов Execution events сохраняются. Неизвестные события, некорректная последовательность событий, несовпадение статуса Execution с терминальным событием и другие уже выявляемые противоречия не исправляются автоматически, а приводят к RecoveryError.
- **REQ-10:** Инициализация и закрытие ExecutionRecorder встроены в жизненный цикл приложения без утечки соединения; ошибка восстановления не приводит к запуску UserInterface.
- **REQ-11:** Новые и существующие тесты доказывают требования REQ-01—REQ-10. Документация MODULE_CONTRACTS.md соответствует фактическому контракту после изменений.

## 6. Ограничения и правила

### 6.1 Фиксированные решения

- Базовый commit — `main@1b4d709d0f391a847727c34abf2b50a841436463`.
- SQLite остаётся источником истины для состояния задач и подтверждений.
- Существующие RecoveryManager, StateManager, ApprovalManager и ExecutionRecorder переиспользуются.
- Автоматически переводить задачу в SUCCEEDED разрешено только при доказанно успешном последнем Execution и валидной истории событий.
- Неопределённые задачи остаются в исходном статусе и возвращаются в диагностическом результате.
- Противоречивые данные вызывают RecoveryError; интерфейс при этом не запускается.
- Восстановление не выполняет и не повторяет никаких действий.
- Существующие контракты approval и терминальных TaskStatus сохраняются.

### 6.2 Делегированные решения

- Конкретные имена и размещение новых типов результата восстановления.
- Минимальная структура типизированных unresolved-диагностик, обеспечивающая REQ-05 и REQ-06.
- Способ тестирования порядка startup-вызова с изоляцией файловой системы и внешних компонентов.
- Организация context manager/try-finally для закрытия ExecutionRecorder, если соблюдены REQ-01, REQ-02 и REQ-10.

### 6.3 Запрещённая работа

- Не переносить в 10.A персистентный прогресс Adapter, возобновление плана или idempotency внешних действий.
- Не менять поведение инструментов, ExecutionBackend, GitTool и механизмов approval.
- Не менять схему БД, если требования можно выполнить на текущих таблицах.
- Не подавлять RecoveryError и не продолжать запуск UI при противоречивом состоянии.
- Не объявлять RUNNING/CREATED задачи завершёнными только по отсутствию Execution.
- Не добавлять универсальный retry, rollback или exactly-once механизм.
- Не выполнять несвязанный рефакторинг.

### 6.4 Git-полномочия для этой задачи

- **Разрешено без отдельного подтверждения:** создать рабочую ветку `stage-10a-automatic-recovery` от указанного baseline; изменять только разрешённые файлы; выполнять локальные проверки; создавать commits в этой feature-ветке; отправить feature-ветку и открыть Draft PR в `main` после завершения реализации и отчёта.
- **Требует отдельного разрешения:** merge PR, push непосредственно в `main`, force-push, переписывание общей истории.
- **Запрещено:** reset/clean/restore с риском потери пользовательских данных, удаление веток, изменения вне scope и любые операции над локальной копией пользователя без его участия.
- **При сомнении:** остановиться и запросить постановщика.

### 6.5 Общие ограничения

- Изучить актуальные исходники и связанные тесты до изменения кода.
- Не дублировать существующую функциональность и не создавать новые менеджеры или уровни абстракции без обоснованной необходимости.
- Не менять публичные контракты и поведение за пределами задачи без отдельного согласования.
- Не расширять объём задачи самостоятельно.
- Не ослаблять и не удалять существующие тесты ради прохождения проверок.
- Не заявлять о выполнении команды или проверки, если она фактически не запускалась.
- При обнаружении противоречия, блокера или необходимости выйти за рамки задачи остановиться и запросить решение постановщика.
- Если фактический baseline отличается от указанного, не адаптировать задачу молча: остановиться и сообщить Planner.

## 9. Критерии приёмки

- **AC-01 (REQ-01, REQ-10):** startup создаёт RecoveryManager с компонентами, связанными с тем же файлом SQLite; ExecutionRecorder корректно закрывается.
- **AC-02 (REQ-02, REQ-10):** тест подтверждает, что recover вызывается ровно один раз до UserInterface.run(), а при RecoveryError UI не запускается.
- **AC-03 (REQ-03):** валидная последняя успешная запись Execution переводит RUNNING задачу в SUCCEEDED; терминальные задачи остаются неизменными.
- **AC-04 (REQ-04):** pending approvals переживают повторное создание компонентов и остаются доступны с теми же ID; корректная WAITING_FOR_APPROVAL задача классифицируется как ожидающая, противоречия дают RecoveryError.
- **AC-05 (REQ-05, REQ-06):** CREATED/RUNNING состояния без достаточных доказательств возвращаются как unresolved с task_id, статусом и причиной; статус задачи не меняется.
- **AC-06 (REQ-07):** повторный вызов не создаёт повторных переходов, approvals или событий и не приводит к ошибке.
- **AC-07 (REQ-08):** в тестах подтверждено отсутствие вызова Executor/инструментов и повторного выполнения при восстановлении.
- **AC-08 (REQ-09):** тесты подтверждают, что повреждённая или противоречивая история приводит к RecoveryError и не исправляется молча.
- **AC-09 (REQ-11):** MODULE_CONTRACTS.md точно описывает новый контракт и фактическую интеграцию запуска.
- **AC-10 (REQ-11):** целевые тесты, полный pytest, Ruff и diff check выполнены; все результаты привязаны к проверенному HEAD и указаны в отчёте.

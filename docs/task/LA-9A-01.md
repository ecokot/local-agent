# Задание LA-9A-01 — Исследование интеграции локального GitTool

## 1. Идентификация

- **Проект:** local-agent
- **Этап / подэтап:** 9.А
- **ID задачи:** LA-9A-01
- **Название:** Исследование существующей архитектуры и подготовка плана реализации GitTool
- **Базовая ветка и commit:** `main` / `22763a8df21211aa28e32c9a19bf6adba7dcfc83`
- **Постановщик:** Планировщик проекта
- **Исполнитель:** Разработчик

## 2. Контекст

Этап 9 посвящён безопасной Git-интеграции. Git должен быть обычным инструментом существующей системы, а не отдельной подсистемой или менеджером.

Предварительное направление: `Orchestrator → ToolExecutorAdapter → ToolExecutor → GitTool → локальный git.exe`.

Существующие решения:
- Git работает с локальным репозиторием.
- Push/Pull и GitHub-синхронизация не входят в базовую реализацию этапа 9, пока отдельно не согласованы.
- Пользовательские изменения нельзя затирать.
- Сброс репозитория допускается только с явного согласия пользователя.
- Подтверждение связано с конкретной операцией и её параметрами; изменение параметров требует нового подтверждения.
- Отказ пользователя означает, что операция не выполняется.
- Автоматический reset/clean для устранения ошибок запрещён.

Исследовать актуальные исходники и тесты, в частности ToolExecutor, ApprovalManager, Workspace, RunCommandTool, ExecutionBackend, ExecutionRecorder, Orchestrator, ToolExecutorAdapter, модели Plan/PlanStep и существующие инструменты.

## 3. Цель и ожидаемый результат

Изучить текущую архитектуру и подготовить минимальный технически обоснованный план внедрения локального GitTool в существующий исполнительный контур. Определить необходимые изменения, безопасный набор операций, правила разрешений, тесты и последовательность подэтапов реализации.

Это исследовательская задача. Код и документация проекта не изменяются.

## 4. Объём работ

Разрешено и требуется:
- исследовать действующие контракты и реализации, связанные с исполнением инструментов, разрешениями, рабочей областью и журналированием;
- изучить релевантные тесты;
- определить способ локального запуска Git на Windows;
- предложить ограниченный набор Git-операций и классифицировать их по уровню риска;
- подготовить минимальный план следующих подэтапов.

Не входит в задачу:
- реализация GitTool или любых других компонентов;
- изменение исходников, тестов, документации и плана;
- создание веток, коммитов и PR;
- push/Pull и GitHub-синхронизация;
- создание GitManager, GitCoordinator или отдельной подсистемы Git;
- выполнение произвольных Git-команд, сформированных моделью.

## 5. Требования

- **REQ-01:** Изучить реальный контракт ToolExecutor: регистрацию инструментов, параметры, разрешения, выполнение и журналирование. Указать минимальный способ регистрации GitTool.
- **REQ-02:** Изучить ApprovalManager и определить, как применять существующий механизм подтверждений к Git-операциям. Подтверждение должно относиться к конкретному действию и параметрам.
- **REQ-03:** Изучить Workspace и ExecutionBackend. Обосновать способ работы GitTool с локальным репозиторием Windows, не используя Docker для управления Git-репозиторием.
- **REQ-04:** Изучить RunCommandTool, GetDiffTool и другие релевантные инструменты. Разделить переиспользуемые механизмы и функции, которые GitTool должен реализовать самостоятельно.
- **REQ-05:** Определить, как результаты Git-операций будут записываться через существующий ExecutionRecorder без дублирования системы истории.
- **REQ-06:** Определить защиту незакоммиченных пользовательских изменений, правила проверки исходного состояния, отдельной ветки, diff, состава изменённых файлов, конфликтов и ошибок. Сброс/удаление/перезапись пользовательских изменений допускаются только после явного подтверждения; отказ означает отмену операции.
- **REQ-07:** Предложить минимальный набор Git-операций первой версии и разделить их на безопасные без подтверждения, изменяющие состояние и потенциально разрушающие с обязательным подтверждением. Отдельно рассмотреть reset, clean, restore/checkout, удаление веток и принудительное перемещение указателей веток.
- **REQ-08:** Подготовить последовательный план подэтапов реализации. Для каждого указать цель, scope, предполагаемые файлы/контракты, зависимости, тесты и проверяемые критерии приёмки.

## 6. Ограничения и правила

- Только исследование. Не изменять код, тесты, документацию и plan.MD.
- Не создавать ветки, коммиты и PR.
- Не выполнять Git-операции, изменяющие рабочее состояние репозитория.
- Не создавать отдельный Git-менеджер или ненужные абстракции.
- Не предлагать произвольный запуск команд Git, передаваемых моделью.
- Не расширять scope и не начинать реализацию.
- Все выводы подтверждать ссылками на актуальные файлы, классы, методы, контракты и тесты.
- При обнаружении противоречия с принятыми решениями остановиться и указать его в отчёте.

## 7. Планируемые изменения

Изменения в проектном коде и документации не предполагаются. Ожидается только исследовательский отчёт по шаблону `docs/report/REPORT_TEMPLATE.md`.

## 8. Тестирование и проверки

Код не меняется, поэтому запуск полного pytest/Ruff не требуется. Не выполнять команды, изменяющие репозиторий.

Обязательно:
- изучить релевантные существующие тесты;
- привести их точные пути и объяснить, какие контракты они подтверждают;
- подтвердить, что после исследования рабочее дерево и ветка не изменялись, если исполнитель имеет доступ к Git-состоянию.

## 9. Критерии приёмки

- **AC-01 (REQ-01):** Контракт ToolExecutor описан по реальным исходникам; предложен минимальный способ регистрации GitTool.
- **AC-02 (REQ-02):** Показано, как существующий ApprovalManager может подтверждать Git-действия с привязкой к параметрам.
- **AC-03 (REQ-03):** Обоснован локальный способ запуска Git на Windows и объяснено, почему Docker ExecutionBackend для этой задачи не подходит.
- **AC-04 (REQ-04):** Указано, что можно переиспользовать из существующих инструментов, а что требует отдельной реализации внутри GitTool.
- **AC-05 (REQ-05):** Описано журналирование Git-операций через существующую историю.
- **AC-06 (REQ-06):** Предложены конкретные меры защиты пользовательских изменений, включая запрет автоматического сброса.
- **AC-07 (REQ-07):** Представлен минимальный перечень Git-операций с классификацией разрешений и подтверждений.
- **AC-08 (REQ-08):** Предложено логичное разбиение реализации на небольшие подэтапы с тестами и критериями.
- **AC-09:** Исследование проведено без изменения исходников, тестов и документации.

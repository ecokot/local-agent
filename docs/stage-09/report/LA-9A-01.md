## 2. Краткий результат

Исследованы реальные реализации и тесты исполнительного контура: `ToolExecutor`, `ApprovalManager`, `Workspace`, `ExecutionBackend`, `RunCommandTool`, `GetDiffTool`, `ExecutionRecorder`, `ToolExecutorAdapter`, `Orchestrator`, модели плана и связанные тесты.

Основной вывод: Git следует добавить как обычный специализированный инструмент в существующий контур:

`Orchestrator → ToolExecutorAdapter → ToolExecutor → GitTool → локальный git.exe`

Отдельный GitManager/GitCoordinator не требуется. Для GitTool нужен ограниченный набор типизированных операций с фиксированным построением аргументов процесса. Передавать модели произвольный список аргументов Git или командную строку нельзя.

Для доступа к репозиторию на Windows GitTool должен запускать установленный Git for Windows непосредственно на хосте через `subprocess`, с массивом аргументов, `shell=False`, `cwd=Workspace.root`, ограничением времени и размера вывода. Существующий `ExecutionBackend` предназначен для запуска кода в Docker и не должен использоваться для управления Git-метаданными репозитория.

В первой версии предлагается ограничиться диагностическими/read-only операциями и небольшим набором строго контролируемых изменений состояния. Разрушительные операции не включать. Перед изменениями необходимо фиксировать исходное состояние репозитория, проверять HEAD/index/worktree и состав файлов; при сомнении — отказывать в операции, а не пытаться автоматически «починить» репозиторий.

Исходный код и тесты не изменялись. Добавляется только этот отчёт.

## 6. Технические решения и отклонения

### 6.1. Интеграция в существующий контур

Фактический маршрут исполнения плана:

1. `Orchestrator.execute_approved_plan()` передаёт одобренный Plan в Executor.
2. `ToolExecutorAdapter.execute()` проходит по PlanStep и передаёт `step.action` и `step.parameters` в ToolExecutor.
3. `ToolExecutor.execute()` разрешает только зарегистрированные имена инструментов, проверяет параметры, управляет подтверждением и журналированием.
4. GitTool выполняет конкретную разрешённую операцию через локальный Git.

`PlanStep.action` сейчас является строкой, а `parameters` — словарём. Это позволяет добавить имена Git-действий без введения отдельного маршрутизатора. Неизвестные действия уже отклоняются реестром ToolExecutor.

### 6.2. Предлагаемый контракт GitTool

- Один специализированный класс GitTool в `src/local_agent/execution/tools/git.py` (или `git_tool.py`, окончательное имя зафиксировать в постановке реализации).
- Конструктор получает существующий Workspace и, при необходимости, настройки timeout/output limit.
- Внешний контракт — фиксированные операции и строгие параметры. Никакого параметра `command`, `args` или сырой командной строки, напрямую передаваемой в subprocess.
- Внутри GitTool каждой операции соответствует собственный заранее определённый набор аргументов Git.
- Запуск: `subprocess.run([...], cwd=workspace.root, shell=False, capture_output=True, text=True, encoding="utf-8", errors="replace", timeout=...)`.
- Исполняемый файл: обнаруживать `git.exe` через PATH (например, `shutil.which("git")`); при отсутствии Git возвращать понятную типизированную ошибку.
- Проверять репозиторий через `git rev-parse --show-toplevel`; корень должен совпадать с Workspace.root. Не принимать случайный родительский репозиторий, найденный Git при запуске из вложенной папки.
- Разбирать stdout/stderr, exit code и timeout в типизированный результат. Не считать exit code 0 единственным источником смысла для команд, у которых отсутствие ветки/объекта является штатным результатом.
- Все пути проверять через Workspace и передавать после разделителя `--`; не допускать path traversal и интерпретацию пользовательского имени файла как опции или pathspec magic.
- Не использовать `shell=True`, `cmd.exe /c`, PowerShell или сборку одной командной строки из параметров модели.

### 6.3. Операции первой версии и разрешения

**Без подтверждения — только чтение:**

- проверка наличия Git и принадлежности Workspace репозиторию;
- `status --porcelain=v1` (включая untracked);
- текущая ветка и HEAD;
- список локальных веток;
- ограниченный `log`;
- `diff` рабочего дерева и отдельно staged diff;
- список изменённых файлов.

**С обязательным подтверждением — изменение состояния:**

- создание новой ветки с проверкой уникальности имени и текущего HEAD;
- добавление в index только явно перечисленных и разрешённых файлов;
- создание commit с подтверждением точного staged diff, списка файлов, HEAD и commit message.

Подтверждение должно показывать человеку фактическую операцию и её последствия. Для commit необходимо убедиться, что в index нет посторонних staged changes. Нельзя включать в commit изменения только потому, что они уже присутствуют в index.

**Не поддерживать в первой версии:**

- `reset` (включая `--hard` и перемещение HEAD);
- `clean`;
- `restore`;
- `checkout` для переключения/восстановления файлов;
- принудительное перемещение указателей веток (`branch -f`, `update-ref`, force-подобные действия);
- удаление веток;
- stash/pop/drop;
- merge/rebase/cherry-pick/revert;
- push/pull/fetch и GitHub-синхронизацию;
- любые произвольные команды, сформированные моделью.

Даже если отдельная операция Git может быть безопасной при определённых условиях, в первой версии предпочтительнее не предоставлять её вовсе, чем полагаться на эвристическое распознавание опасных аргументов.

### 6.4. Защита пользовательских изменений

1. До начала исполнения задачи получить и сохранить baseline: HEAD, состояние index, tracked/untracked status и отпечатки релевантных файлов.
2. Если на старте уже есть staged changes или неоднозначные изменения, разрешать диагностику, но блокировать stage/commit до явного решения пользователя. Не пытаться автоматически сохранить их через stash.
3. После выполнения файловых действий повторно получить status и diff; сопоставить список изменённых путей с файлами, которые задача действительно должна была изменить.
4. Для stage принимать только явный список файлов. Не применять `git add .`, `git add -A` или добавление всего каталога.
5. Перед commit проверять неизменность HEAD, состав index, staged diff и отсутствие неожиданных файлов. Любое расхождение требует остановки и нового решения пользователя.
6. Не выполнять автоматические reset/clean/restore/checkout/stash для устранения конфликтов. Отказ пользователя означает, что Git-операция не выполняется.
7. Для подтверждения изменяющей операции включать контрольное состояние репозитория в параметры approval, чтобы подтверждение не переиспользовалось после изменения HEAD или diff.

Ограничение: один лишь `git status` не позволяет достоверно отличить конкурентное пользовательское редактирование того же файла от изменений агента. Поэтому реализация должна дополнительно опираться на исходные отпечатки файлов/результаты операций записи и прекращать commit при невозможности доказать происхождение изменения. Нельзя обещать абсолютную защиту от параллельной записи без такого контроля.

### 6.5. Журналирование

Существующий ExecutionRecorder уже обеспечивает привязку execution к task, события, SQLite, JSONL и восстановление недописанных trace. Новая история Git не нужна.

В событиях Git-операций следует сохранять:
- фиксированное имя операции;
- безопасные параметры (repo root, branch, конкретные относительные пути, message);
- контрольные значения до/после (HEAD и краткие fingerprints);
- exit code, timeout, ограниченные stdout/stderr;
- итоговый статус и нормализованную ошибку.

Нельзя без ограничений записывать полный вывод, diff больших файлов или потенциальные секреты. Существующую рекурсивную маскировку чувствительных ключей следует сохранить; при необходимости добавить отдельные тесты на секреты в выводе и commit metadata.

## 2. Краткий результат

Исследованы реальные реализации и тесты исполнительного контура: `ToolExecutor`, `ApprovalManager`, `Workspace`, `ExecutionBackend`, `RunCommandTool`, `GetDiffTool`, `ExecutionRecorder`, `ToolExecutorAdapter`, `Orchestrator`, модели плана и связанные тесты.

Основной вывод: Git следует добавить как обычный специализированный инструмент в существующий контур:

`Orchestrator → ToolExecutorAdapter → ToolExecutor → GitTool → локальный git.exe`

Отдельный GitManager/GitCoordinator не требуется. Для GitTool нужен ограниченный набор типизированных операций с фиксированным построением аргументов процесса. Передавать модели произвольный список аргументов Git или командную строку нельзя.

Для доступа к репозиторию на Windows GitTool должен запускать установленный Git for Windows непосредственно на хосте с фиксированными аргументами, без shell, с `cwd=Workspace.root`, ограничением времени и размера вывода. Для завершения Git вместе с hooks/потомками выбран Windows Job Object: Git создаётся suspended, назначается в job до ResumeThread, а timeout завершает весь job через TerminateJobObject. Существующий `ExecutionBackend` предназначен для запуска кода в Docker и не должен использоваться для управления Git-метаданными репозитория.

В первой версии предлагается ограничиться диагностическими/read-only операциями и небольшим набором строго контролируемых изменений состояния. Разрушительные операции не включать. Для изменяющих операций фактическое состояние репозитория снимается до запроса approval и включается в хешируемые параметры подтверждения; после approval состояние снимается повторно непосредственно перед Git-командой. Несовпадение HEAD, index или fingerprints блокирует выполнение и создаёт новый запрос подтверждения для нового состояния. Вывод subprocess ограничивается во время чтения потоков, а не после полного накопления. Пути файлов передаются Git в literal pathspec mode.

Исходный код и тесты не изменялись. Добавляется только этот отчёт.

## 6. Технические решения и отклонения

### 6.1. Интеграция в существующий контур

Фактический маршрут исполнения плана:

1. `Orchestrator.execute_approved_plan()` передаёт одобренный Plan в Executor.
2. `ToolExecutorAdapter.execute()` проходит по PlanStep и передаёт `step.action` и `step.parameters` в ToolExecutor.
3. `ToolExecutor.execute()` разрешает только зарегистрированные имена инструментов, проверяет параметры, управляет подтверждением и журналированием.
4. GitTool выполняет конкретную разрешённую операцию через локальный Git.

`PlanStep.action` сейчас является строкой, а `parameters` — словарём. Это позволяет добавить имена Git-действий без введения отдельного маршрутизатора. Неизвестные действия уже отклоняются реестром ToolExecutor.

### 6.2. Предлагаемый контракт GitTool

- Один специализированный класс GitTool в src/local_agent/execution/tools/git.py (или git_tool.py; окончательное имя фиксируется в постановке реализации).
- Конструктор получает существующий Workspace и настройки timeout, лимита stdout и лимита stderr.
- Внешний контракт — фиксированные операции и строгие параметры. Параметры command, args или сырая командная строка, напрямую передаваемая subprocess, запрещены.
- На Windows запуск реализовать через Win32 `CreateProcessW` с `CREATE_SUSPENDED` и перенаправленными stdout/stderr pipe handles (не через `Popen.terminate()`/`Popen.kill()`, которые не завершают дерево). Создать Job Object и установить `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; вызвать `AssignProcessToJobObject` до `ResumeThread`. Командная строка формируется из фиксированного executable и экранированного списка аргументов, shell не используется. Для других платформ допустим отдельный runner, но Windows-путь является обязательным для проекта.
- Два reader-потока параллельно читают stdout и stderr небольшими чанками. Каждый сохраняет в памяти только первые MAX_OUTPUT_BYTES, отмечает truncation и продолжает вычитывать/отбрасывать остаток до EOF. Так дочерний процесс не блокируется из-за заполненного pipe, а объём накопленной памяти ограничен двумя лимитами плюс фиксированные буферы чтения.
- Основной поток ждёт процесс до timeout. При timeout вызывает `TerminateJobObject(job, exit_code)`, затем `WaitForSingleObject` для процесса и дожидается завершения reader-потоков с ограниченным временем. После завершения job все унаследованные write handles закрываются и readers должны получить EOF. Если reader не завершился в заданный срок, вызывается `CancelSynchronousIo` для его native thread handle; затем закрываются pipe handles и выполняется финальный bounded join. Любая ошибка завершения дерева или cleanup возвращается как отдельная ошибка инструмента, а не маскируется обычным timeout. В `finally` закрываются process/thread handles, Job Object и все pipe handles; закрытие Job Object дополнительно обеспечивает `KILL_ON_JOB_CLOSE` как страховку при аварийном выходе.
- Декодировать только сохранённые байты как UTF-8 с errors="replace", нормализовать переводы строк; вернуть exit code, timeout и отдельные флаги truncation. Ошибка reader-потока приводит к ошибке инструмента после гарантированного cleanup.
- Исполняемый файл обнаруживать через shutil.which("git"); при отсутствии Git возвращать понятную типизированную ошибку.
- Проверять репозиторий через git rev-parse --show-toplevel; корень должен совпадать с Workspace.root. Учитывать linked worktree: .git может быть файлом, указывающим на общий gitdir.
- Каждый путь проверять через Workspace. Для операций с pathspec передавать глобальный флаг --literal-pathspecs до подкоманды и разделитель -- перед списком путей: git --literal-pathspecs add -- <relative-path>. -- завершает разбор опций, но сам по себе не отключает pathspec magic. Не конструировать pathspec из шаблонов модели.
- Не использовать shell=True, cmd.exe /c, PowerShell или сборку одной командной строки из параметров модели.
### 6.3. Операции первой версии и разрешения

**Без подтверждения — только чтение:**

- проверка наличия Git и принадлежности Workspace репозиторию;
- `status --porcelain=v1` (включая untracked);
- текущая ветка и HEAD;
- список локальных веток;
- ограниченный `log`;
- `diff` рабочего дерева и отдельно staged diff;
- список изменённых файлов.

**С обязательным подтверждением — изменение состояния:**

- создание новой ветки с одновременным переключением на неё (одна операция `git switch -c`), после проверки уникальности имени, ожидаемого HEAD и чистоты рабочего дерева/index;
- добавление в index только явно перечисленных и разрешённых файлов;
- создание commit с подтверждением точного staged diff, списка файлов, HEAD и commit message.

Подтверждение должно показывать человеку фактическую операцию и её последствия. Для commit необходимо убедиться, что в index нет посторонних staged changes. Нельзя включать в commit изменения только потому, что они уже присутствуют в index.

**Не поддерживать в первой версии:**

- `reset` (включая `--hard` и перемещение HEAD);
- `clean`;
- `restore`;
- `checkout` для переключения/восстановления файлов;
- принудительное перемещение указателей веток (`branch -f`, `update-ref`, force-подобные действия);
- удаление веток;
- stash/pop/drop;
- merge/rebase/cherry-pick/revert;
- push/pull/fetch и GitHub-синхронизацию;
- любые произвольные команды, сформированные моделью.

Даже если отдельная операция Git может быть безопасной при определённых условиях, в первой версии предпочтительнее не предоставлять её вовсе, чем полагаться на эвристическое распознавание опасных аргументов.

### 6.3.1. Точное поведение операции создания ветки

Операция первой версии — **создать новую ветку и сразу переключиться на неё**. Это единый пользовательски подтверждаемый шаг, реализуемый фиксированной командой `git switch -c <branch> <expected-head>` (или эквивалентом с теми же проверками). Вариант «только создать ветку, оставив текущую активной» не входит в контракт: он не переводит дальнейшую работу агента на изолированную ветку и создаёт риск продолжить изменения в исходной ветке.

Перед выполнением GitTool обязан проверить, что имя ветки допустимо и ещё не занято, текущий HEAD совпадает с подтверждённым `expected_head`, а index и worktree чисты, включая отсутствие untracked-файлов. При любом изменении состояния после запроса подтверждения операция отклоняется и требуется новое подтверждение. Если рабочее дерево не чистое, GitTool ничего не переключает и не пытается автоматически сохранять изменения через stash, reset, clean или иные команды. Самостоятельное переключение на уже существующую ветку и отдельная операция switch также не поддерживаются в первой версии.

### 6.4. Защита пользовательских изменений

#### Двухфазное подтверждение изменяющей Git-операции

Текущий ToolExecutor.execute() вызывает ApprovalManager.request_approval() до definition.execute(**parameters). Поэтому snapshot только внутри GitTool после approval недостаточен: фактическое состояние должно входить в подтверждаемые параметры заранее. Предлагается добавить в _ToolDefinition необязательный callback подготовки approval-контекста только для изменяющих Git-действий; отдельный менеджер не создаётся.

1. **До запроса approval:** ToolExecutor вызывает read-only GitTool.inspect_state(operation, parameters). Метод возвращает JSON-совместимый snapshot: canonical resolved repo root; полный HEAD; текущую ветку; результат git write-tree (tree SHA текущего index); SHA-256 вывода git ls-files --stage -z; SHA-256 git status --porcelain=v2 -z; SHA-256 git diff --binary --no-ext-diff; для каждого затрагиваемого и untracked-файла — нормализованный относительный путь, тип/размер и SHA-256 содержимого, вычисленный потоково. Для stage/commit включаются точный список путей и ожидаемый staged diff; для commit также message. Если write-tree завершается ошибкой из-за unmerged index, изменяющая операция блокируется.
2. **Формирование approval:** ToolExecutor добавляет snapshot во внутренние approval-параметры рядом с исходными параметрами операции. ApprovalManager._serialize_parameters() уже канонизирует JSON с сортировкой ключей и считает SHA-256; значит snapshot становится частью идентичности подтверждаемого действия. Snapshot не принимается от модели и не является пользовательским параметром: он формируется только локальным GitTool.
3. **После решения пользователя:** когда request_approval() возвращает APPROVED, ToolExecutor повторно вызывает inspect_state() непосредственно перед исполнением и сравнивает весь snapshot с подтверждённым. is_approved() проверяется для параметров с тем же snapshot.
4. **Если состояние изменилось:** GitTool не вызывается. ToolExecutor вызывает request_approval() с новым фактическим snapshot и прежними параметрами операции. Другой hash создаёт новый pending approval; ToolExecutor возвращает WAITING_FOR_APPROVAL. Старое подтверждение не переносится на новое состояние. Если состояние снова стало в точности прежним, существующий approval может быть найден по идентичному snapshot — это та же операция над тем же зафиксированным состоянием.
5. **Непосредственно перед mutating subprocess:** GitTool получает snapshot ещё раз и сравнивает с expected snapshot. Несовпадение означает отказ без запуска Git-команды и требует нового approval. После операции состояние проверяется повторно и записывается в ExecutionRecorder. Это сужает TOCTOU-окно, но не устраняет возможность внешней записи в микропромежутке между последней проверкой и запуском Git; для index дополнительно учитывать Git index lock, а после команды проверять postcondition. Не заявлять абсолютную защиту от параллельной записи, которую текущий код не обеспечивает.

Если на старте уже есть staged changes, конфликты или файлы вне ожидаемого набора, stage/commit блокируются до явного решения пользователя. Stage получает только явный список путей; git add . и git add -A запрещены. Автоматические reset/clean/restore/checkout/stash не выполняются. При конфликте, смене HEAD, index, status или fingerprints операция отменяется; пользовательские изменения не исправляются автоматически.
### 6.5. Журналирование

Существующий ExecutionRecorder уже обеспечивает привязку execution к task, события, SQLite, JSONL и восстановление недописанных trace. Новая история Git не нужна.

В событиях Git-операций следует сохранять:
- фиксированное имя операции;
- безопасные параметры (repo root, branch, конкретные относительные пути, message);
- контрольные значения до/после (HEAD и краткие fingerprints);
- exit code, timeout, ограниченные stdout/stderr;
- итоговый статус и нормализованную ошибку.

Нельзя без ограничений записывать полный вывод, diff больших файлов или потенциальные секреты. Существующую рекурсивную маскировку чувствительных ключей следует сохранить; при необходимости добавить отдельные тесты на секреты в выводе и commit metadata.

## 7. Предлагаемый последовательный план подэтапов реализации

План является рекомендацией исследования, а не утверждённой постановкой. Каждый следующий подэтап начинать только после приёмки предыдущего.

### 9.Б — Контракт и read-only GitTool

- **Цель:** определить и реализовать минимальный безопасный интерфейс GitTool для чтения состояния локального репозитория. Windows 11 — обязательная целевая платформа этого подэтапа.
- **Scope:** типы операций/результатов/ошибок; поиск git.exe; Windows runner на Win32 API: создание Git через `CreateProcessW` с `CREATE_SUSPENDED`, перенаправленными stdout/stderr pipe handles и без shell; создание Job Object, установка `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, назначение процесса через `AssignProcessToJobObject` до `ResumeThread`; bounded streaming stdout/stderr reader-потоками (каждый reader сохраняет не более заданного лимита байтов, остаток продолжает вычитывать и отбрасывать); timeout с завершением всего дерева через `TerminateJobObject`; ограниченное ожидание завершения readers, `CancelSynchronousIo` при зависшем чтении и гарантированное закрытие pipe/process/thread/job handles в cleanup; literal pathspec для операций с путями (`--literal-pathspecs` до подкоманды плюс `--` перед путями); проверка корня репозитория; status, current branch, HEAD, branch list, log и diff. Создание веток и переключение не входят в этот подэтап.
- **Платформенная граница:** описанный Job Object runner обязателен на Windows и не заменяется `subprocess.Popen`, `Popen.terminate()` или `Popen.kill()`. Реализация для других ОС не входит в 9.Б; если она понадобится, её следует спроектировать отдельным платформенным runner с собственным механизмом завершения дерева процессов и отдельными критериями приёмки. Она не должна менять или ослаблять обязательный Windows-путь.
- **Предполагаемые файлы/контракты:** новый src/local_agent/execution/tools/git.py; при необходимости небольшой внутренний модуль Windows process runner; экспорт в tools/__init__.py при необходимости; новые test/test_git_tool.py и тесты runner.
- **Зависимости:** Workspace; системный Git for Windows; Win32 API для процессов, Job Objects и синхронизации.
- **Тесты:** подменённые Win32 API-вызовы проверяют точный порядок: CreateJobObject/configure limits → CreateProcessW с CREATE_SUSPENDED → AssignProcessToJobObject → ResumeThread; при ошибке AssignProcessToJobObject ResumeThread не вызывается, а созданные handles закрываются. Проверить, что stdout/stderr читаются параллельно и сохраняется не более лимита при продолжении drain; timeout вызывает TerminateJobObject, ожидает завершения процесса и reader-потоков с ограниченным временем; зависшее чтение прерывается через CancelSynchronousIo; все pipe/process/thread/job handles закрываются и при успехе, и при ошибках. Интеграционный тест с тестовым дочерним процессом/hook подтверждает, что потомок входит в Job Object, завершается при TerminateJobObject и больше не удерживает pipe handles. Проверить страховку JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE, отказ при несовместимом внешнем Job Object, reader exception и cleanup; literal pathspec (`--literal-pathspecs` и `--`), Git отсутствует, неверный root, non-zero exit, dirty/untracked/staged state.
- **Критерии приёмки:** только фиксированные read-only операции; Windows runner запускает процесс suspended и назначает его в Job Object до ResumeThread; timeout завершает весь Job Object; readers завершаются в bounded срок, handles гарантированно очищаются; память вывода ограничена во время чтения; literal pathspec проверен тестами; произвольной команды нет; рабочее дерево тестами не меняется.
### 9.В — Регистрация GitTool в ToolExecutor и передача через Adapter

- **Цель:** сделать read-only Git-операции доступными как обычные действия плана.
- **Scope:** внедрить GitTool в конструктор ToolExecutor, зарегистрировать фиксированные action names и параметры; для read-only действий оставить обычный маршрут, для mutating действий подключить подготовку approval snapshot до request_approval() и повторное сравнение после approval; проверить прохождение через ToolExecutorAdapter и Orchestrator.
- **Предполагаемые файлы/контракты:** execution/tool_executor.py, agents/tool_executor_adapter.py (только если понадобится; предпочтительно без изменения), wiring приложения, test/test_tool_executor.py, test/test_tool_executor_adapter.py.
- **Зависимости:** принятый 9.Б.
- **Тесты:** неизвестная операция отклоняется; read-only не создают approval; mutating operation передаёт фактический snapshot в approval parameters; после approval выполняется повторный inspect; изменившийся HEAD/index/status/fingerprint приводит к новому WAITING_FOR_APPROVAL и нулевому числу mutating Git-вызовов; неизменный snapshot допускает выполнение; ошибка Git не маскируется как успех.
- **Критерии приёмки:** Git-действия проходят существующий исполнительный маршрут; snapshot строится до approval и сверяется после approval; изменение состояния приводит к новому подтверждению без вызова Git; отдельного менеджера/маршрутизатора нет; старые инструменты продолжают работать.
### 9.Г — Безопасные изменяющие операции и подтверждения

- **Цель:** добавить ограниченные операции, необходимые для изоляции работы задачи и фиксации результата.
- **Scope:** одна операция create_and_switch_branch на основе git switch -c: создать новую ветку и немедленно переключиться на неё; отдельное создание без переключения и отдельное переключение не предоставлять. Перед операцией требовать чистые index/worktree (включая untracked), ожидаемый HEAD и свободное имя ветки. Далее — stage только явного списка путей с --literal-pathspecs и --; commit; двухфазный approval snapshot (HEAD, index tree/entries, status, tracked diff и fingerprints файлов), повторная проверка непосредственно перед mutating subprocess и новый approval при любом расхождении.
- **Предполагаемые файлы/контракты:** GitTool; ToolExecutor; при необходимости минимальная передача task context из Adapter; тесты GitTool, ApprovalManager, ToolExecutor и Adapter.
- **Зависимости:** принятые 9.Б и 9.В.
- **Тесты:** pending approval не запускает mutating Git; approval после перезапуска сохраняется; изменение исходных параметров или любого поля snapshot (HEAD, index tree/entries, status, tracked diff, fingerprint затрагиваемого/untracked-файла) создаёт новый pending approval и не выполняет операцию; отказ не выполняет операцию; pre-existing staged changes блокируют commit; изменение между повторной проверкой и запуском Git обнаруживается защитной проверкой/lock; неожиданный файл блокирует stage/commit; commit содержит только подтверждённый staged diff.
- **Критерии приёмки:** approval содержит фактический snapshot, полученный до запроса; snapshot повторно проверяется после approval и непосредственно перед mutating subprocess; любое расхождение требует нового подтверждения и не запускает команду; пользовательские правки не сбрасываются; нет автоматического stash/reset/clean; stage/commit используют literal pathspec и проверенный точный список файлов.
### 9.Д — Сквозные проверки и фиксация ограничений

- **Цель:** подтвердить работу GitTool на реальном временном локальном репозитории и регрессионно проверить безопасность.
- **Scope:** интеграционные сценарии на временном Git-репозитории; журналирование операций; документация фактического контракта и запретов.

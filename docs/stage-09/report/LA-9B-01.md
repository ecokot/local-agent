## 2. Краткий результат

Добавлены самостоятельный read-only `GitTool`, внутренний Windows runner на Win32 API, unit-тесты и Windows integration tests. Реализованы восемь операций: `status`, `branch`, `head`, `branches`, `log`, `diff`, `staged_diff`, `changed_files`. Git обнаруживается через `shutil.which("git")`; команды и аргументы формируются внутри GitTool, запускаются без shell с `cwd=Workspace.root`. Корень репозитория проверяется через `git rev-parse --show-toplevel`.

Windows runner создаёт Job Object с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, запускает процесс через `CreateProcessW(CREATE_SUSPENDED)`, назначает его в Job Object через `AssignProcessToJobObject` и только затем вызывает `ResumeThread`. stdout/stderr читаются параллельно; каждый поток сохраняет не более заданного лимита, продолжая вычитывать остаток. При timeout применяется `TerminateJobObject`; reader-потоки ограниченно ожидаются, а при зависании вызывается `CancelSynchronousIo`.

Фактические проверки пользователя прошли: полный набор — 430 passed, 3 skipped; Windows integration file — 2 passed; Ruff и diff check — без замечаний. При этом проверка постановки выявила неполное покрытие части обязательных негативных сценариев: нет тестов на отказ ряда Win32 API, отказ `AssignProcessToJobObject` до `ResumeThread`, reader exception/cancellation и некоторые Git-сценарии. Поэтому успешный запуск имеющихся тестов не означает полного выполнения REQ-02–REQ-08. Отчёт фиксирует эти пробелы; решение о приёмке не заявляется.

## 6. Технические решения и отклонения

- **Принятые решения:**
  - Git запускается непосредственно через найденный `git.exe`, не через Docker ExecutionBackend и не через shell.
  - GitTool принимает `Workspace`, проверяет корень через `rev-parse --show-toplevel` и задаёт `cwd=Workspace.root`.
  - Разрешён фиксированный набор из восьми read-only операций; произвольный executable/command/args вызывающим кодом не задаётся.
  - Для всех вызовов используется `--literal-pathspecs`; фильтры путей передаются после `--`.
  - Runner: `CreateJobObjectW` → настройка `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` → pipes и stdin NUL → `CreateProcessW(CREATE_SUSPENDED)` → `AssignProcessToJobObject` → `IsProcessInJob` → `ResumeThread`.
  - stdout/stderr читаются двумя потоками; сохраняемый лимит — **1 MiB на каждый поток**. Остаток вычитывается и отбрасывается.
  - Timeout GitTool по умолчанию — **15 секунд**, верхняя граница конфигурации — **120 секунд**. Время ограниченного cleanup reader/process — **2 секунды на ожидание**.
  - При timeout вызывается `TerminateJobObject`; если reader не завершился после закрытия Job Object, вызывается `CancelSynchronousIo`.
  - Максимальный лимит `log` — **100 коммитов**, значение по умолчанию — **20**.
- **Отклонения от постановки:** архитектурных отклонений не зафиксировано. Добавление `.gigaide/` в `.gitignore` выполнено по просьбе пользователя и указано в разделе 5.
- **Изменения публичных контрактов:** нет.
- **Не выполнено:** полное тестовое покрытие ошибок Win32 API, отказа AssignProcessToJobObject, reader exception/cancellation/cleanup, linked worktree, detached HEAD и всех комбинаций состояний Git.
- **Известные ограничения и риски:** реализация основных сценариев есть, но перечисленные выше ветви не имеют достаточного автоматического подтверждения. В частности, нельзя считать полностью доказанными bounded cleanup при всех ошибках Win32 и корректность парсинга всех вариантов rename/copy записей porcelain v2.

- **Рекомендуемое состояние:** требуется продолжение работы до независимой проверки. Успешный полный pytest и Ruff подтверждают отсутствие регрессий в выполненных проверках, но не закрывают пробелы покрытия, перечисленные в постановке.

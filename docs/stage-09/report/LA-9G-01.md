## 2. Краткий результат

Добавлены три фиксированных изменяющих Git-действия:

1. `git_create_and_switch_branch(branch_name)`
2. `git_stage(paths)`
3. `git_commit(message, paths)`

Действия зарегистрированы в существующем `ToolExecutor`, каждое требует отдельного approval. До approval выполняются только read-only проверки. Snapshot включается в канонические параметры существующего `ApprovalManager`; после approval состояние повторно проверяется под per-repository lock и ещё раз непосредственно перед mutating subprocess. Изменившийся snapshot блокирует исходную команду и создаёт новый pending approval.

Stage receipt хранится в существующих SQLite execution events `ExecutionRecorder`, а не в новом хранилище. Поэтому подтверждённый результат stage доступен после пересоздания `ToolExecutor` и перезапуска процесса. `MODULE_CONTRACTS.md` обновлён. `plan.MD` и `docs/DEVELOPMENT_HISTORY.md` не изменялись.

**Статус:** реализация подготовлена к локальной проверке пользователем. Приёмка не заявляется: целевые и полные тесты, Ruff и diff check в целевой Windows-среде ещё не запускались.

## 6. Технические решения и отклонения

- **Approval hash:** использован существующий ApprovalManager. Snapshot передаётся как часть canonical parameters; отдельный approval store не создавался.
- **Stage receipt:** хранится в существующей таблице `execution_events` через `ExecutionRecorder.finish_execution()`. JSONL не используется как источник истины.
- **Restart:** ApprovalManager и stage receipt переживают restart. Повторный вызов ToolExecutor с тем же task/action/parameters возобновляет approved action. Полное восстановление позиции ToolExecutorAdapter не реализовано существующей архитектурой и в этой задаче не расширялось.
- **Lock:** общий `threading.RLock` по canonical repository root; потоки одного процесса сериализованы, разные repository независимы. Внешние процессы lock не соблюдают.
- **Последняя проверка:** snapshot повторно снимается непосредственно перед командой. Если он отличается, execution фиксируется как FAILED, создаётся новый pending approval, mutating subprocess не запускается.
- **Hooks/filters:** операции branch/commit блокируются при активных Git hooks или настроенном `core.hooksPath`; stage блокируется для путей с внешним clean filter. `core.fsmonitor=false` задаётся фиксированным параметром Git, а status запускается с `--no-optional-locks`.
- **Commit signing:** отключён только для фиксированного commit subprocess, чтобы не запускать внешний signing program.
- **Отклонения:** отдельные ApprovalManager/Adapter изменения не потребовались. Никаких действий push/merge в main, reset/clean/restore/stash и destructive rollback не выполнялось.
- **Ограничения:** lock не синхронизирует внешние процессы; после timeout или postcondition failure никакой автоматический rollback не выполняется. При частичном Git-сбое состояние может требовать ручной диагностики.

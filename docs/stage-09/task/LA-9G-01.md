## 2. Контекст

Подэтапы 9.А–9.В приняты. На базовом commit реализован read-only `GitTool` в `src/local_agent/execution/tools/git.py`, его восемь операций зарегистрированы в существующем `ToolExecutor` и вызываются через `ToolExecutorAdapter`. `ApprovalManager` сохраняет approvals в SQLite и связывает их с `task_id`, `action_type` и SHA-256 канонически сериализованных параметров; approvals переживают перезапуск.

Исследование 9.А определяет для 9.Г три ограниченные операции: создать и сразу переключиться на новую ветку, stage только явного списка путей, commit подтверждённого staged-содержимого. Оно требует snapshot Git-состояния, повторную проверку после подтверждения и защиту пользовательских изменений.

До изменения кода Developer обязан изучить актуальные `MODULE_CONTRACTS.md`, `docs/stage-09/report/LA-9A-01.md`, исходники и тесты GitTool, ToolExecutor, ToolExecutorAdapter, ApprovalManager, Workspace и моделей approvals. Документация не заменяет проверку фактической реализации.

## 3. Цель и ожидаемый результат

Добавить три фиксированные Git-операции, каждая из которых требует отдельного пользовательского approval, связанного с точными параметрами и фактическим snapshot репозитория. После approval Python повторно проверяет состояние и выполняет только одобренное действие. Любое расхождение блокирует запуск команды и требует нового approval.

Пользовательские изменения нельзя автоматически удалять, перезаписывать, прятать или сбрасывать. Lock приложения не защищает от произвольных внешних процессов; остаточное ограничение должно быть явно описано, без заявления об абсолютной атомарности.

## 4. Объём работ

Разрешено и требуется:
- Расширить существующий GitTool тремя фиксированными изменяющими операциями.
- Интегрировать snapshot и двухфазную проверку в существующий ToolExecutor/ApprovalManager/SQLite flow.
- Минимально изменить Adapter только если фактически необходим task context.
- Сериализовать изменяющие Git-действия local-agent для одного repository/workspace.
- Добавить unit- и integration-тесты на временных локальных Git-репозиториях.
- При необходимости обновить MODULE_CONTRACTS.md и создать отчёт `docs/stage-09/report/LA-9G-01.md`.

Не входит:
- Push, pull, fetch, merge, rebase, cherry-pick, revert, удаление веток, GitHub API.
- `reset`, `clean`, `restore`, stash, произвольный checkout/switch, изменение Git config, произвольные Git-команды.
- Произвольные executable/args/pathspec от модели; `git add .` и `git add -A`.
- Отдельный GitManager/GitCoordinator, отдельный approval store или новый журнал Git.
- Несвязанный рефакторинг, изменения Orchestrator/Reviewer/VerificationExecutor вне прямой необходимости.
- Изменение `plan.MD` и `docs/DEVELOPMENT_HISTORY.md`; closeout — отдельная задача.

## 5. Требования

- **REQ-01:** GitTool предоставляет ровно три новых фиксированных действия:
  1. `git_create_and_switch_branch(branch_name: str)`: создать локальную ветку от текущего HEAD и сразу переключиться на неё одной фиксированной командой. Отклонять detached HEAD, существующее имя, некорректное имя и любое dirty-состояние (staged, unstaged, untracked, conflicts).
  2. `git_stage(paths: list[str])`: stage только непустой явный список уникальных относительных путей workspace. Отклонять пустой список, дубликаты, абсолютные пути, NUL, traversal, pathspec magic, wildcard и недопустимые/неоднозначные пути.
  3. `git_commit(message: str, paths: list[str])`: commit только непустое сообщение и непустой явный список путей; разрешать только точное совпадение staged diff с одобренным набором путей и содержимым, без дополнительных staged/unstaged/untracked/conflict изменений.
- **REQ-02:** Все три действия зарегистрированы в существующем ToolExecutor как требующие approval. До approval ни один mutating subprocess не запускается; обход ToolExecutor/ApprovalManager невозможен.
- **REQ-03:** До создания approval Python снимает фактический детерминированный snapshot. Он включает как минимум canonical repository/workspace root, branch/detached state, полный HEAD SHA, porcelain-v2 status с NUL-safe parsing, index tree/fingerprint, staged и unstaged diff fingerprints, tracked/untracked/conflict entries, а также нормализованный относительный путь, тип/режим и content fingerprint (либо состояние отсутствия) каждого выбранного пути. Snapshot входит в параметры, hash которых вычисляет существующий ApprovalManager.
- **REQ-04:** После APPROVED, включая resume после restart, Python снимает snapshot заново. Любое изменение параметров или snapshot блокирует исходную команду и создаёт новый pending approval для нового состояния. Отменённый hash остаётся окончательно отменённым.
- **REQ-05:** Непосредственно перед каждым mutating subprocess повторно проверяются snapshot и preconditions под общей блокировкой изменяющих действий local-agent для этого repository. Lock удерживается через проверку и subprocess и сериализует действия приложения для одного репозитория; разные репозитории не должны без причины блокировать друг друга.
- **REQ-06:** Создание ветки разрешено только в полностью чистом репозитории, при существующем HEAD и свободном валидном имени. После команды проверить новую текущую ветку и сохранение исходного HEAD.
- **REQ-07:** Stage принимает только одобренные пути, передаёт их с `--literal-pathspecs` и `--`, проверяет postcondition index и неизменность исходных файлов. Неожиданное изменение останавливает дальнейшие операции; автоматический unstage/reset/restore запрещён.
- **REQ-08:** Commit проверяет HEAD, index tree, staged paths и fingerprints staged-содержимого перед запуском. После запуска проверить новый HEAD, parent SHA и tree/path/content commit относительно одобренного staged tree. Empty commit и любое несовпадение блокируются/возвращаются как ошибка; автоматический reset/amend запрещён.
- **REQ-09:** Pre-existing staged changes не могут попасть в commit неявно. Stage/commit отклоняются при исходном index, не соответствующем чистому индексу, кроме index, созданного предыдущим одобренным stage-действием этой задачи и подтверждённого его результатом. Изменения вне явного набора, конфликтные состояния и неожиданные файлы блокируют операцию, если нарушают точную проверку состояния. Пользовательские файлы не удалять.
- **REQ-10:** Сохраняются timeout и output limits существующего Windows runner. Git unavailable, invalid parameters, non-zero exit, timeout, changed snapshot и failed postcondition дают явный неуспех, не маскируются под успех.
- **REQ-11:** Документировать, что per-repository lock защищает только действия local-agent. Внешние Git/файловые процессы lock не соблюдают. Не заявлять абсолютную атомарность между последней проверкой и Git syscall; при невозможности доказать безопасное состояние — остановить операцию и сообщить причину.
- **REQ-12:** Существующие read-only операции и approvals не регрессируют; SQLite остаётся источником истины, JSONL (если используется) — только проекцией истории.

## 6. Ограничения и правила

### 6.1 Фиксированные решения
- Только три действия REQ-01; никакого произвольного Git.
- Отдельный approval на каждое действие; snapshot включён в hash.
- Повторная проверка после approval и непосредственно перед subprocess.
- Никакого автоматического stash/reset/clean/restore/unstage для исправления расхождений.
- Существующие Workspace, GitTool, ToolExecutor, ApprovalManager и Windows runner — основа реализации.

### 6.2 Делегированные решения
- Внутренние типы snapshot/result/error и безопасный алгоритм fingerprint.
- Конкретные read-only Git plumbing команды для index/tree/path/commit проверки.
- Реализация per-repository lock без новой самостоятельной подсистемы.
- Приватные helper-функции и организация тестов.

### 6.3 Запрещённая работа
- Не ослаблять snapshot до одного HEAD или текстового status.
- Не полагаться на модель как источник истины о состоянии Git.
- Не использовать shell, произвольные args, wildcard, `git add .` или `git add -A`.
- Не менять пользовательские файлы ради чистого состояния.
- Не делать destructive cleanup/rollback после частичного сбоя.
- Не создавать новые менеджеры/реестры/хранилища approvals.

### 6.4 Git-полномочия для этой задачи
- **Разрешено без отдельного подтверждения:** read-only Git в проектном репозитории; mutating Git только в тестовых временных репозиториях.
- **Требует отдельного разрешения:** любые изменяющие Git-действия в пользовательском проектном репозитории; публикация ветки/PR и merge — только по явному разрешению пользователя.
- **Запрещено:** push в main, force-push, reset/clean/restore/stash, удаление веток, переписывание истории, merge/rebase/pull/fetch.
- **При сомнении:** остановиться и запросить постановщика.

### 6.5 Общие ограничения
- Изучить актуальные исходники и тесты до изменения кода.
- Не менять публичные контракты за пределами задачи.
- Не ослаблять и не удалять существующие тесты.
- Не заявлять о проверках, которые фактически не запускались.
- В отчёте явно указывать, кто запускал проверки; если пользователь — написать «Тесты запускал пользователь».
- При риске потери данных, противоречии или необходимости расширить scope — остановиться и запросить решение.

## 8. Тестирование и проверки

### 8.1 Кто запускает проверки

| Проверка / среда | Ответственный | Как передаётся результат |
|---|---|---|
| Целевые тесты и полный pytest в среде Developer | Developer | Фактические команды и результаты в отчёте |
| Windows-проверки в локальной среде пользователя, если среда Developer не эквивалентна | Пользователь | Planner выдаёт команды; пользователь присылает вывод |
| Ruff и diff check | Developer; пользователь повторно при необходимости | Фактический вывод |
| CI, если настроен | CI | Ссылка на run и статус |

### 8.2 Обязательные проверки
- [ ] Pending approval, cancellation и отказ не запускают mutating subprocess.
- [ ] Approval сохраняется в SQLite и возобновляется после restart.
- [ ] Изменение параметров, HEAD, branch, index tree, status, staged/unstaged diff, untracked/conflict entries или fingerprint выбранного файла после approval создаёт новый pending approval; старая команда не выполняется.
- [ ] Изменение выбранного файла пользователем между approval и resume блокирует старое подтверждение.
- [ ] Создание ветки: чистое состояние проходит; dirty/staged/untracked/conflict/detached/existing branch/invalid name блокируются без изменений.
- [ ] Stage затрагивает только точные выбранные пути; пробелы, Unicode, leading dash и pathspec magic обрабатываются безопасно; абсолютный путь, traversal, NUL, wildcard, duplicate и пустой список отклоняются.
- [ ] Stage не изменяет содержимое файлов; index postcondition точен; неожиданные изменения не откатываются автоматически.
- [ ] Commit включает только подтверждённые staged paths/content; лишний staged path, unstaged change, conflict, пустой commit или изменённый index блокируют действие.
- [ ] Commit postcondition проверяет HEAD, parent и точный tree/path/content.
- [ ] Git errors, timeout, output limit, invalid workspace и failed postcondition возвращают неуспех.
- [ ] Конкурентные mutating действия local-agent одного репозитория сериализованы; независимые репозитории не блокируют друг друга.
- [ ] Ограничение внешнего процесса и поведение при обнаруженном расхождении задокументированы.
- [ ] Все существующие read-only GitTool, ToolExecutor, Adapter и ApprovalManager тесты проходят.
- [ ] Полный `uv run pytest -v`, `uv run ruff check .`, `git diff --check` проходят.
- [ ] Проверены полный diff и список файлов относительно актуальной `origin/main`.

## 9. Критерии приёмки

- **AC-01 (REQ-01):** реализованы ровно три фиксированных действия с указанными параметрами и валидацией; произвольные Git-операции недоступны.
- **AC-02 (REQ-02):** каждое действие проходит ToolExecutor/ApprovalManager; тестами доказано отсутствие mutating subprocess до APPROVED.
- **AC-03 (REQ-03):** фактический детерминированный snapshot включён в approval parameters и его hash.
- **AC-04 (REQ-04):** snapshot повторно проверяется после resume; любое расхождение требует нового pending approval и не выполняет старую команду; SQLite restart/cancel semantics протестированы.
- **AC-05 (REQ-05, REQ-11):** per-repository lock сериализует действия приложения; повторная проверка идёт под lock непосредственно перед subprocess; внешнее ограничение честно описано.
- **AC-06 (REQ-06):** создание ветки проходит только в чистом репозитории и подтверждает новую ветку/неизменный HEAD; остальные состояния блокируются.
- **AC-07 (REQ-07, REQ-09):** stage меняет index только для одобренного списка; пользовательские файлы не изменяются; unexpected state останавливает операцию без отката.
- **AC-08 (REQ-08, REQ-09):** commit содержит ровно одобренное staged-содержимое; pre/postconditions подтверждены тестами.
- **AC-09 (REQ-10, REQ-12):** ошибки не маскируются; read-only операции и текущий approval flow не регрессируют; SQLite остаётся source of truth.
- **AC-10 (REQ-01–REQ-12):** целевые/полные тесты, Ruff и diff check имеют фактические результаты; отчёт отвечает на все REQ/AC и PR содержит только согласованный scope.

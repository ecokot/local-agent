# LA-9C-01 — Интеграция read-only GitTool в исполнительную цепочку

## 1. Идентификация

- **Проект:** local-agent
- **Этап / подэтап:** 9.В
- **ID задачи:** LA-9C-01
- **Название:** Регистрация GitTool в ToolExecutor и передача вызовов через ToolExecutorAdapter
- **Базовая ветка и commit:** `main`, `45e273611657b807f741eb2a4fe66e500a476741`
- **Постановщик:** Project Planner
- **Исполнитель:** Project Developer

## 2. Контекст

На базовом commit `45e2736` самостоятельный read-only `GitTool` уже реализован в `src/local_agent/execution/tools/git.py`. Он принимает `Workspace`, проверяет, что Workspace.root является корнем Git-репозитория, и предоставляет восемь фиксированных операций:

- `status()`
- `branch()`
- `head()`
- `branches()`
- `log(limit=20)`
- `diff(paths=())`
- `staged_diff(paths=())`
- `changed_files()`

Результаты и ошибки типизированы в том же модуле. Unit-тесты находятся в `test/test_git_tool.py`, Windows integration tests — в `test/integration/test_git_tool_windows.py`.

Сейчас `ToolExecutor` в `src/local_agent/execution/tool_executor.py` регистрирует фиксированный набор инструментов через `_ToolDefinition`, проверяет имена обязательных/необязательных параметров, запрашивает approval только для явно помеченных действий, записывает выполнение через `ExecutionRecorder` и преобразует ожидаемые ошибки в `ToolExecutionResult`.

`ToolExecutorAdapter` в `src/local_agent/agents/tool_executor_adapter.py` уже передаёт `PlanStep.action` и `PlanStep.parameters` в `ToolExecutor.execute(task_id, tool_name, parameters)`. Отдельный Git-маршрут в Adapter не нужен, если тесты подтвердят корректную передачу без преобразований.

Текущие связанные тесты:
- `test/test_tool_executor.py`
- `test/test_tool_executor_adapter.py`
- `test/test_git_tool.py`
- `test/integration/test_git_tool_windows.py`

Технические контракты и план на начало задачи сверены с базовым commit, указанным выше. `plan.MD` является единственным источником статусов и решений о приёмке.

## 3. Цель и ожидаемый результат

Подключить уже существующий `GitTool` к фиксированному реестру `ToolExecutor`, чтобы одобренный пользователем план мог вызывать только заранее определённые read-only Git-действия по цепочке:

`Orchestrator → ToolExecutorAdapter → ToolExecutor → GitTool`.

Вызовы Git должны проходить через обычный исполнительный контур: строгую проверку параметров, запись выполнения в `ExecutionRecorder`, единый формат результата/ошибки и существующую обработку плана в Adapter. Ни одна Git-операция этого подэтапа не должна требовать approval, поскольку все восемь действий строго read-only.

## 4. Объём работ

Разрешено и требуется:

- Добавить существующий `GitTool` как зависимость `ToolExecutor` и зарегистрировать его фиксированные действия в `_tools`.
- Использовать следующие фиксированные имена действий (это публичный интерфейс PlanStep):
  - `git_status`
  - `git_branch`
  - `git_head`
  - `git_branches`
  - `git_log`
  - `git_diff`
  - `git_staged_diff`
  - `git_changed_files`
- Передавать параметры непосредственно соответствующему методу GitTool; не добавлять универсальный dispatcher, произвольные команды, executable, shell или Git args.
- Для действий без аргументов принимать только пустой словарь параметров.
- Для `git_log` разрешить необязательный параметр `limit`; при отсутствии использовать существующее значение GitTool по умолчанию.
- Для `git_diff` и `git_staged_diff` разрешить необязательный параметр `paths`; при отсутствии использовать существующее значение GitTool по умолчанию. Список путей должен передаваться в GitTool без конкатенации команд или shell-строк.
- Сохранять типизированные результаты GitTool в поле `ToolExecutionResult.result` без потери содержимого; ошибки GitTool возвращать как `FAILED` с диагностическим сообщением и корректно завершать запись ExecutionRecorder.
- Проверить полный маршрут через Adapter на Plan с Git-действиями, включая успешные вызовы и ошибочные/некорректные параметры.
- Добавить unit- и integration-level тесты, не требующие доступа к реальному пользовательскому репозиторию. Использовать временный Git-репозиторий и/или контролируемый fake GitTool/runner там, где это уместно.
- Обновить `MODULE_CONTRACTS.md`, если изменились публичный конструктор ToolExecutor, перечень действий или связи модулей.

Не входит в задачу:

- Любые изменяющие Git-операции, включая checkout/switch, branch create/delete, add, reset, restore, commit, merge, rebase, cherry-pick, stash.
- push, pull, fetch, remote configuration и любые сетевые Git-операции.
- Approval snapshot, новые механизмы подтверждений или изменение ApprovalManager.
- Изменения Orchestrator, Plan/PlanStep или формата плана, если необходимость не доказана текущим контрактом; при такой необходимости остановиться и запросить решение.
- Создание GitManager, нового менеджера, общего Git dispatcher или дополнительного слоя абстракции.
- Повторная реализация GitTool, Windows runner или уже покрытых в 9.Б функций.
- Перестройка ToolExecutorAdapter. Его существующий прозрачный путь передачи параметров следует использовать; менять Adapter только при обнаружении конкретного препятствия, предварительно сообщив постановщику.

## 5. Требования

- **REQ-01:** ToolExecutor принимает уже созданный экземпляр GitTool как зависимость и регистрирует все восемь фиксированных действий с точными именами, перечисленными в разделе 4.
- **REQ-02:** Все Git-действия read-only и выполняются без запроса approval; произвольное имя действия, команда Git или дополнительные параметры не могут быть переданы в обход allowlist.
- **REQ-03:** Валидация имён параметров точная: действия без аргументов не принимают параметры; git_log принимает только limit; git_diff и git_staged_diff принимают только paths. Типы и значения параметров проверяются GitTool и/или явной валидацией ToolExecutor до запуска Git.
- **REQ-04:** Результаты восьми методов GitTool передаются вызывающему коду через ToolExecutionResult.result без потери значимых полей/элементов; ошибки GitTool дают FAILED и понятную диагностику.
- **REQ-05:** Каждый фактически начатый вызов GitTool журналируется существующим ExecutionRecorder; успех завершает запись как SUCCEEDED, ожидаемая ошибка — как FAILED. Отклонённые до исполнения неизвестные действия и параметры не запускают GitTool и не создают ложную запись успешного выполнения.
- **REQ-06:** PlanStep с Git-действием проходит через существующий ToolExecutorAdapter без специального обходного маршрута; step_results содержат action, parameters, execution_id и результат.
- **REQ-07:** Тесты покрывают каждое действие, строгие границы параметров, отсутствие approval, обработку ошибок, журналирование и сквозную передачу через Adapter. Существующее поведение остальных инструментов не регрессирует.
- **REQ-08:** Документация технических контрактов соответствует фактическим сигнатурам, реестру действий и цепочке вызова после изменений.

## 6. Ограничения и правила

- Изучить актуальные исходники и связанные тесты до изменения кода; постановка основана на проверке базового commit `45e2736`, но перед реализацией сверить рабочую ветку с этим commit.
- Сохранять существующие контракты `ToolExecutionResult`, `ExecutionRecorder`, `ToolExecutorAdapter` и GitTool.
- Не менять реализацию GitTool из 9.Б, кроме исправления доказанного блокирующего дефекта после согласования.
- Не ослаблять и не удалять существующие тесты.
- Не добавлять Git-действия в список approval-required; не менять правила подтверждения остальных действий.
- Не ловить произвольные исключения широким `except Exception` только ради преобразования ошибки. Обрабатывать типизированные ошибки GitTool в соответствии с существующим стилем ToolExecutor.
- Не считать отсутствие изменений в Adapter недостатком: если существующий путь передачи подтверждён интеграционными тестами, Adapter остаётся без изменений.
- Если для создания GitTool требуется новый composition root или изменение жизненного цикла Workspace, выходящее за существующий конструкторный контракт, остановиться и запросить решение.
- Не выполнять push, merge, reset, clean, удаление веток и другие значимые Git-действия без отдельного явного разрешения пользователя.
- В отчёте обязательно указывать, кто запускал каждую проверку. Пользовательские локальные прогоны нельзя приписывать Developer.

## 8. Тестирование и проверки

Обязательные проверки:

- [ ] Целевые unit-тесты ToolExecutor и GitTool-интеграции.
- [ ] Целевые тесты ToolExecutorAdapter, включая последовательность нескольких Git-действий в одном Plan.
- [ ] Тесты строгой валидации: лишний параметр, пропущенный/неверный limit, неверный тип paths, недопустимый путь; Git runner не должен вызываться при отклонении параметров.
- [ ] Тесты отсутствия approval для всех восьми Git-действий.
- [ ] Тесты SUCCEEDED/FAILED и статуса ExecutionRecorder при успешном вызове и типизированной ошибке GitTool.
- [ ] Тесты неизвестного Git-действия и попытки передать параметры, похожие на произвольные Git args/команды.
- [ ] `uv run pytest -v`.
- [ ] `uv run ruff check .`.
- [ ] `git diff --check origin/main...HEAD`.
- [ ] Проверка полного diff и списка файлов относительно базового commit.

В отчёте указать точные команды, результаты и исполнителя каждой проверки. Если Windows-only integration tests из 9.Б не затрагивались, повторный запуск не обязателен; полный pytest всё равно обязателен на контрольной точке.

## 9. Критерии приёмки

- **AC-01 (REQ-01):** ToolExecutor регистрирует ровно восемь утверждённых Git-действий и вызывает соответствующие методы переданного экземпляра GitTool.
- **AC-02 (REQ-02):** Ни одно Git-действие не запрашивает approval; неизвестные действия и произвольные команды/args отклоняются до вызова GitTool.
- **AC-03 (REQ-03):** Тесты подтверждают точные наборы допустимых имён параметров и отклонение неверных типов/значений до запуска Git.
- **AC-04 (REQ-04):** Для каждого действия проверены тип и содержимое результата; типизированные ошибки GitTool превращаются в FAILED с сохранением диагностики.
- **AC-05 (REQ-05):** ExecutionRecorder получает корректную последовательность событий и финальный статус для успешных и неуспешных фактических вызовов; отклонённые входные данные не создают ложных записей выполнения.
- **AC-06 (REQ-06):** Adapter выполняет план как минимум из нескольких Git-действий через ToolExecutor; step_results сохраняют ожидаемые action, parameters, execution_id и result.
- **AC-07 (REQ-07):** Целевые тесты, полный pytest и Ruff проходят; тесты существующих инструментов не ослаблены и не удалены.
- **AC-08 (REQ-08):** MODULE_CONTRACTS.md обновлён при изменении контракта и точно отражает проверенный код; если публичные контракты не менялись, отсутствие его изменения обосновано в отчёте.
- **AC-09:** Diff не содержит изменяющих Git-операций, approval snapshot, лишних менеджеров, изменений Orchestrator/Plan и несогласованного рефакторинга; отчёт полностью заполнен по шаблону.

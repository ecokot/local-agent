## 2. Контекст

Подэтап 9.А (исследование GitTool) и подэтап 9.Б (реализация read-only GitTool) приняты. В проекте уже существует `GitTool` в `src/local_agent/execution/tools/git.py`. Он предоставляет операции чтения состояния Git-репозитория и использует существующий безопасный механизм запуска локального Git-процесса.

Цель текущей задачи — подключить уже существующий GitTool к общему контуру инструментов. Задача не предполагает повторной реализации GitTool или изменения его поведения.

До изменений изучить как минимум:
- `src/local_agent/execution/tools/git.py` — публичный интерфейс и валидация GitTool;
- `src/local_agent/execution/tool_executor.py` — регистрация и диспетчеризация инструментов, валидация параметров, обработка результатов и ошибок;
- `src/local_agent/execution/tool_executor_adapter.py` — существующий маршрут вызова ToolExecutor из Orchestrator;
- связанные composition/call sites, где создаётся ToolExecutor;
- `test/test_git_tool.py`, `test/test_tool_executor.py` и `test/test_tool_executor_adapter.py` (или фактические соответствующие файлы в текущей структуре);
- `MODULE_CONTRACTS.md`.

Если фактические имена или расположение файлов отличаются, сначала установить актуальную структуру и отразить её в отчёте. Не создавать параллельные реализации.

## 3. Цель и ожидаемый результат

Обеспечить вызов всех восьми read-only операций существующего GitTool через общий ToolExecutor и существующий ToolExecutorAdapter. Вызовы должны использовать общие механизмы диспетчеризации, валидации имён параметров, записи результата/ошибки в ExecutionRecorder и передачи результата вызывающему контуру.

Read-only действия не должны запрашивать подтверждение ApprovalManager. Интеграция не должна менять Orchestrator или добавлять Git-специфичную логику в Adapter, если существующего общего маршрута достаточно.

## 4. Объём работ

### Разрешено и требуется

1. Передавать существующий экземпляр GitTool в ToolExecutor через constructor injection.
2. Зарегистрировать в ToolExecutor следующие действия:
   - `git_status` → `GitTool.status()` → `GIT_STATUS`;
   - `git_branch` → `GitTool.branch()` → `GIT_BRANCH`;
   - `git_head` → `GitTool.head()` → `GIT_HEAD`;
   - `git_branches` → `GitTool.branches()` → `GIT_BRANCHES`;
   - `git_log` → `GitTool.log()` → `GIT_LOG`;
   - `git_diff` → `GitTool.diff()` → `GIT_DIFF`;
   - `git_staged_diff` → `GitTool.staged_diff()` → `GIT_STAGED_DIFF`;
   - `git_changed_files` → `GitTool.changed_files()` → `GIT_CHANGED_FILES`.
3. Обеспечить передачу параметров для `git_log`, `git_diff` и `git_staged_diff` согласно разделу 5.
4. Использовать существующий ToolExecutorAdapter без Git-специфичных изменений, если текущего общего механизма достаточно.
5. Обновить тесты ToolExecutor и Adapter, добавить регрессионные проверки.
6. Обновить `MODULE_CONTRACTS.md` в части фактического контракта интеграции.
7. Сохранить отчёт в `docs/stage-09/report/LA-9C-01.md` по обязательному шаблону.

### Не входит в задачу

- Реализация или изменение внутренних алгоритмов GitTool.
- Добавление изменяющих Git-состояние операций (add, commit, checkout, switch, restore, reset, clean, branch delete, push, pull, merge и т. п.).
- Изменение Orchestrator, Plan, ApprovalManager или общей архитектуры Adapter без доказанной необходимости и отдельного согласования.
- Создание GitManager, отдельного GitAdapter или новых менеджеров/абстракций.
- Изменение `plan.MD`.
- Изменение существующих семи инструментов, кроме минимальных корректировок, необходимых для сохранения совместимости; такие корректировки должны быть объяснены и покрыты тестами.

## 5. Требования

- **REQ-01:** ToolExecutor получает существующий экземпляр GitTool через внедрение зависимости. ToolExecutor не создаёт собственный GitTool внутри себя и не создаёт второй экземпляр при диспетчеризации.
- **REQ-02:** ToolExecutor регистрирует восемь действий и отображает их на указанные методы GitTool и соответствующие типы действий:
  - `git_status` → `status()` → `GIT_STATUS`;
  - `git_branch` → `branch()` → `GIT_BRANCH`;
  - `git_head` → `head()` → `GIT_HEAD`;
  - `git_branches` → `branches()` → `GIT_BRANCHES`;
  - `git_log` → `log()` → `GIT_LOG`;
  - `git_diff` → `diff()` → `GIT_DIFF`;
  - `git_staged_diff` → `staged_diff()` → `GIT_STAGED_DIFF`;
  - `git_changed_files` → `changed_files()` → `GIT_CHANGED_FILES`.
- **REQ-03:** Все восемь Git-действий являются read-only и не инициируют запрос ApprovalManager. Для них используется существующий общий механизм выполнения и записи результата/ошибки в ExecutionRecorder.
- **REQ-04:** `git_status`, `git_branch`, `git_head`, `git_branches` и `git_changed_files` не принимают пользовательских параметров. Передача лишних параметров должна быть отклонена существующей валидацией ToolExecutor до вызова GitTool.
- **REQ-05:** `git_log` принимает необязательный параметр `limit` типа `int`, по умолчанию 20. Допустимый диапазон — от 1 до 100 включительно. Значения типа `bool` недопустимы, несмотря на то что в Python `bool` является подклассом `int`. Неизвестные имена параметров отклоняются до вызова GitTool.
- **REQ-06:** `git_diff` и `git_staged_diff` принимают необязательный параметр `paths` типа `list[str]`, по умолчанию пустой список. Значения передаются существующим методам GitTool без потери элементов; проверка безопасности и допустимости путей остаётся ответственностью GitTool. Неизвестные имена параметров отклоняются до вызова GitTool.
- **REQ-07:** Вызовы через ToolExecutorAdapter доходят до соответствующего Git-действия ToolExecutor и возвращают результат по существующему контракту Adapter. Специальная Git-логика в Adapter не добавляется.
- **REQ-08:** Ошибки GitTool и ошибки валидации обрабатываются и записываются через существующий механизм ToolExecutor/ExecutionRecorder. Ошибка одного вызова не должна приводить к скрытому успешному результату.
- **REQ-09:** Существующие семь инструментов и их поведение остаются совместимыми; их регрессионные тесты продолжают проходить.
- **REQ-10:** `MODULE_CONTRACTS.md` документирует внедрение GitTool, восемь действий, их параметры и read-only характер интеграции. Отчёт исполнителя сохранён в `docs/stage-09/report/LA-9C-01.md` и оформлен по `docs/templates/REPORT_TEMPLATE.md`.

## 8. Тестирование и проверки

Обязательные проверки:

- [ ] Тесты регистрации всех восьми действий, точного соответствия action → метод GitTool → тип действия.
- [ ] Тесты constructor injection: ToolExecutor использует переданный экземпляр GitTool и не создаёт собственный.
- [ ] Тесты отсутствия вызовов ApprovalManager для каждого из восьми read-only действий.
- [ ] Тесты параметров действий без аргументов: отсутствие параметров допускается, лишние параметры отклоняются до вызова GitTool.
- [ ] Тесты `git_log`: default 20; граничные значения 1 и 100; отклонение 0, 101, отрицательных значений, строк, дробных значений и bool.
- [ ] Тесты `git_diff` и `git_staged_diff`: default пустой список; передача заданного списка путей; отклонение неизвестных имён параметров и неверного типа контейнера.
- [ ] Тесты успешного выполнения и ошибок GitTool с проверкой соответствующей записи в ExecutionRecorder.
- [ ] End-to-end тесты маршрута через ToolExecutorAdapter для Git-действий.
- [ ] Регрессионные тесты семи существующих инструментов.
- [ ] Полный набор `uv run pytest -v`.
- [ ] `uv run ruff check .`.
- [ ] `git diff --check origin/main...HEAD`.
- [ ] Проверка полного diff и списка изменённых файлов относительно базового commit.

Проверки запускать в доступной среде проекта. В отчёте для каждой команды обязательно указать, кто именно её запускал: Developer, пользователь, CI или другой исполнитель. Не выдавать результаты локальных проверок пользователя за собственные результаты Developer. Если проверка не запускалась, указать это явно.

## 9. Критерии приёмки

- **AC-01 (REQ-01):** Тест подтверждает, что ToolExecutor использует переданный экземпляр GitTool; создание отдельного экземпляра внутри ToolExecutor отсутствует.
- **AC-02 (REQ-02):** Для всех восьми действий тесты подтверждают точные имена действий, вызываемые методы GitTool и соответствующие типы действий.
- **AC-03 (REQ-03):** Для каждого из восьми действий подтверждено отсутствие запроса ApprovalManager; успешные и неуспешные вызовы проходят через существующий ExecutionRecorder.
- **AC-04 (REQ-04):** Действия без параметров работают без аргументов и отклоняют лишние имена параметров до вызова GitTool.
- **AC-05 (REQ-05):** Проверены default 20, допустимые границы 1 и 100, отклонение значений вне диапазона и неверных типов, включая bool.
- **AC-06 (REQ-06):** Проверены default пустого списка, передача списка путей обоим методам, отклонение неизвестных параметров и неверного типа paths; проверка значений путей остаётся в GitTool.
- **AC-07 (REQ-07):** Интеграционный тест подтверждает успешный маршрут вызова через существующий ToolExecutorAdapter без Git-специфичных изменений Adapter.
- **AC-08 (REQ-08):** Тесты подтверждают запись успешных и ошибочных вызовов в ExecutionRecorder и корректное распространение/представление ошибки.
- **AC-09 (REQ-09):** Все существующие тесты семи инструментов и полный набор pytest проходят без регрессий.
- **AC-10 (REQ-10):** `MODULE_CONTRACTS.md` отражает фактический контракт, отчёт существует по указанному пути и полностью соответствует REPORT_TEMPLATE.md с ответами по каждому REQ-ID и AC-ID.
- **AC-11 (REQ-01–REQ-10):** Ruff проходит; `git diff --check origin/main...HEAD` не сообщает ошибок; diff не содержит изменений вне согласованного Scope или неоговорённых файлов.
- **AC-12 (REQ-01–REQ-10):** В отчёте достоверно указаны ветка, базовый и итоговый commit, PR, полный список файлов, фактические результаты проверок и исполнитель каждой проверки. Ветка не слита в `main`.

Задача готова к независимой проверке только при наличии отчёта и фактических доказательств по всем применимым критериям. Самооценка Developer не является решением о приёмке.

## 10. Формат отчёта

Исполнитель обязан заполнить файл `docs/stage-09/report/LA-9C-01.md` по шаблону `docs/templates/REPORT_TEMPLATE.md` и ответить по каждому REQ-ID и AC-ID. Отчёт должен содержать:

Не объявлять задачу принятой. В конце отчёта указать рекомендацию: готово к независимой проверке либо требуется продолжение работы.

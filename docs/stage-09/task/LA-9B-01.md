# Задание LA-9B-01 — Реализация read-only GitTool

## 1. Идентификация

- **Проект:** local-agent
- **Этап / подэтап:** 9.Б
- **ID задачи:** LA-9B-01
- **Название:** Реализация самостоятельного GitTool и Windows runner для безопасного чтения Git-репозитория
- **Базовая ветка и commit:** `main` / `898d64eff790df751fe972ce7f38eaeeda4632c7` (сверить актуальную `origin/main` перед началом работы; если она изменилась, использовать актуальную `main` и указать SHA в отчёте)
- **Постановщик:** Планировщик проекта
- **Исполнитель:** Разработчик

## 2. Контекст

Подэтап 9.А (LA-9A-01) принят. План реализации этапов 9.Б–9.Д утверждён постановщиком 25.11.2026. На 9.Б требуется реализовать самостоятельный GitTool, который выполняет только фиксированные read-only операции с локальным Git-репозиторием. Подключение к ToolExecutor и Orchestrator относится к следующему подэтапу 9.В.

Утверждённая архитектурная граница:

`Orchestrator → ToolExecutorAdapter → ToolExecutor → GitTool → локальный git.exe`

В рамках этой задачи реализуется только GitTool и его внутренний механизм запуска процессов. GitTool пока не регистрируется в ToolExecutor и не вызывается из плана.

### Принятые решения исследования

- Git запускается непосредственно на хосте через установленный Git for Windows. Существующий Docker `ExecutionBackend` не используется для чтения Git-метаданных.
- На Windows обязателен runner на Win32 API: `CreateProcessW` с `CREATE_SUSPENDED`, назначение процесса в Job Object через `AssignProcessToJobObject` до `ResumeThread`, завершение всего Job Object через `TerminateJobObject`.
- В Job Object устанавливается `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; breakaway flags не включаются.
- stdout и stderr читаются параллельно потоками, сохраняющими ограниченное число байтов и продолжающими вычитывать/отбрасывать остаток.
- Git вызывается без shell, только с фиксированным executable и сформированными внутри GitTool аргументами.
- Для pathspec используется `--literal-pathspecs` до подкоманды и `--` перед путями. Сам по себе `--` не отключает Git pathspec magic.
- Корень Git-репозитория должен совпадать с `Workspace.root`. Нужно учитывать linked worktree, где `.git` может быть файлом.
- Новые менеджеры, отдельный Git-журнал и произвольный запуск команд модели не нужны.

### Основные файлы для изучения до реализации

- `src/local_agent/execution/workspace.py` — `Workspace.root`, `resolve_path()`, проверки traversal и symlink/junction.
- `src/local_agent/execution/tool_executor.py` — текущая граница регистрации инструментов (изменять в этой задаче не требуется).
- `src/local_agent/execution/tools/run_command.py` — текущая модель результата команды и ограничения вывода.
- `src/local_agent/execution/backend.py` — существующий Docker backend; не использовать для Git.
- `src/local_agent/execution/recorder.py` и `src/local_agent/execution/models.py` — существующее журналирование (интеграция относится к следующим подэтапам).
- `test/test_workspace.py`, `test/test_run_command.py`, `test/test_execution_backend.py`, `test/test_tool_executor.py`.
- Принятый отчёт исследования: `docs/stage-09/report/LA-9A-01.md`, особенно разделы 6.2–6.6 и 7 (подэтап 9.Б).
- Контракты: `MODULE_CONTRACTS.md`, раздел 3.6.1.
- План: `plan.MD`, этап 9.

Исполнитель обязан проверить актуальное содержимое этих файлов в своей рабочей ветке. Список выше — начальная точка, а не исчерпывающий перечень зависимостей.

## 3. Цель и ожидаемый результат

Реализовать самостоятельный, тестируемый GitTool для Windows 11, который безопасно читает состояние локального Git-репозитория в пределах переданного `Workspace`.

Результат подэтапа:
- типизированные результаты и ошибки GitTool;
- поиск установленного `git.exe`;
- проверка, что `Workspace.root` является корнем Git-репозитория;
- Windows runner с контролируемым завершением дерева процессов;
- ограниченное по памяти чтение stdout/stderr;
- фиксированный набор read-only Git-операций;
- unit- и интеграционные тесты, подтверждающие отсутствие изменения репозитория.

GitTool должен быть пригоден для последующей регистрации в ToolExecutor на 9.В, но сама регистрация в этой задаче не выполняется.

## 4. Объём работ

### Разрешено и требуется

1. Изучить актуальные реализации и тесты перечисленных компонентов.
2. Добавить `src/local_agent/execution/tools/git.py` с классом GitTool либо эквивалентным минимальным публичным интерфейсом.
3. Определить типизированные модели результата и ошибки GitTool. Результат должен позволять отличить:
   - код завершения Git;
   - stdout и stderr;
   - timeout;
   - усечение stdout и stderr;
   - ошибку запуска/runner/cleanup.
4. Найти Git через `shutil.which("git")`. При отсутствии Git возвращать понятную типизированную ошибку.
5. Проверять репозиторий через фиксированный вызов `git rev-parse --show-toplevel`; нормализованный корень должен совпадать с `Workspace.root`. Не отвергать linked worktree только потому, что `.git` является файлом.
6. Реализовать Windows runner:
   - создать Job Object и настроить `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`;
   - создать stdout/stderr pipe handles;
   - запустить Git через `CreateProcessW` с `CREATE_SUSPENDED`;
   - назначить процесс в Job Object через `AssignProcessToJobObject`;
   - только после успешного назначения вызвать `ResumeThread`;
   - при ошибке назначения не возобновлять процесс; завершить/закрыть созданные ресурсы;
   - читать stdout и stderr параллельно отдельными reader-потоками;
   - каждый reader сохраняет не более настроенного byte limit, но продолжает вычитывать и отбрасывать лишние байты до EOF;
   - при timeout вызвать `TerminateJobObject`, дождаться завершения процесса и reader-потоков в ограниченные сроки;
   - если синхронное чтение зависло после завершения job, использовать `CancelSynchronousIo` для соответствующего reader thread, затем закрыть pipe handles и выполнить ограниченное ожидание;
   - в `finally` закрыть все созданные process/thread/job/pipe handles;
   - ошибки завершения дерева процессов и очистки не маскировать под обычный timeout.
7. Сформировать командную строку Win32 из фиксированного пути к executable и внутреннего списка аргументов с корректным Windows quoting. Не использовать shell, `cmd.exe`, PowerShell или конкатенацию сырой пользовательской строки.
8. Ограничить timeout и размеры stdout/stderr разумными положительными значениями, проверять конфигурацию при создании GitTool. Значения по умолчанию и верхние границы выбрать и документировать в коде/тестах.
9. Реализовать только следующие read-only операции:
   - `status` — состояние tracked, staged и untracked изменений;
   - `branch` — текущая ветка (корректно обработать detached HEAD);
   - `head` — полный SHA текущего HEAD;
   - `branches` — список локальных веток;
   - `log` — ограниченный список последних коммитов с валидируемым лимитом;
   - `diff` — diff рабочего дерева;
   - `staged_diff` — diff index относительно HEAD;
   - `changed_files` — список изменённых путей, включая staged, unstaged и untracked.
10. Все Git arguments формировать внутри GitTool. Не принимать от вызывающего кода произвольные `command`, `args`, executable или shell-строку. Если операция поддерживает фильтр путей, принимать только явные относительные пути, проверять их через Workspace и формировать pathspec в literal mode.
11. Сохранять бинарно-безопасный разбор Git-вывода там, где формат допускает произвольные имена файлов (например, NUL-разделённые списки). Не разбирать имена файлов построчно, если это может приводить к неоднозначности.
12. При non-zero exit code возвращать/поднимать определённый контрактом результат ошибки так, чтобы вызывающий код не мог принять неуспешную Git-операцию за успешную.
13. Добавить unit-тесты GitTool и runner. Добавить Windows integration tests с временным Git-репозиторием и тестовым дочерним процессом/hook для проверки Job Object и завершения потомков.
14. При необходимости экспортировать типы из `tools/__init__.py`, но не менять публичные API соседних компонентов без необходимости.
15. Подготовить отчёт по `docs/templates/REPORT_TEMPLATE.md` в `docs/stage-09/report/LA-9B-01.md`.

### Не входит в задачу

- Регистрация GitTool в ToolExecutor, изменения ToolExecutorAdapter и Orchestrator — это 9.В.
- Любые Git-операции, изменяющие состояние: создание/переключение ветки, stage, commit.
- Approval snapshot, изменение ApprovalManager и политика подтверждений — это 9.В/9.Г согласно утверждённому плану.
- Push, Pull, Fetch и GitHub API.
- `reset`, `clean`, `restore`, `checkout`, stash, удаление веток, merge, rebase, cherry-pick, revert и любые другие изменяющие/разрушительные операции.
- Произвольные Git-команды или аргументы от модели/плана.
- Отдельный GitManager/GitCoordinator, отдельный журнал Git или новая подсистема.
- Переписывание Workspace, ExecutionBackend или RunCommandTool.
- Поддержка других ОС в качестве обязательной части этой задачи. Windows 11 — обязательная целевая платформа; не-Windows runner не реализовывать без отдельного согласования.
- Обновление общих контрактов и структуры проекта сверх необходимого для нового инструмента и его тестов. Документацию фактического контракта можно уточнить в рамках этой задачи только в пределах согласованного scope.

## 5. Требования

- **REQ-01:** GitTool реализован как самостоятельный инструмент в `src/local_agent/execution/tools/git.py`, использует переданный `Workspace` и предоставляет типизированные результаты и ошибки. Его публичный интерфейс ограничен фиксированными read-only операциями; регистрации в ToolExecutor нет.
- **REQ-02:** Git executable обнаруживается через `shutil.which("git")`. Отсутствие Git, некорректный Workspace, отсутствие Git-репозитория, несовпадение корня и ошибки Git обрабатываются предсказуемо и не маскируются под успешный результат.
- **REQ-03:** Windows runner использует `CreateProcessW` с `CREATE_SUSPENDED`, назначает процесс в Job Object до `ResumeThread`, включает `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` и не запускает процесс, если назначение в Job Object не удалось.
- **REQ-04:** stdout и stderr читаются параллельно; объём сохраняемых данных ограничен во время чтения, остаток вычитывается и отбрасывается. Timeout завершает всё дерево процессов через `TerminateJobObject`; зависшее чтение ограниченно отменяется; все handles очищаются при успехе и ошибках.
- **REQ-05:** GitTool формирует только фиксированные команды для перечисленных read-only операций. Произвольный executable, command, args или shell-вызов от вызывающего кода невозможны. Любые используемые pathspec обрабатываются в literal mode с `--literal-pathspecs` и разделителем `--`.
- **REQ-06:** Проверка Git-репозитория подтверждает, что `git rev-parse --show-toplevel` соответствует `Workspace.root`; поддерживается корректный случай linked worktree с `.git`-файлом. Все операции выполняются с `cwd=Workspace.root`.
- **REQ-07:** Реализованы и проверены все восемь read-only операций: status, branch, head, branches, log, diff, staged_diff, changed_files. Форматы вывода корректно обрабатывают detached HEAD, staged/unstaged/untracked и имена файлов с пробелами/нестандартными символами.
- **REQ-08:** Тесты покрывают нормальное выполнение, отсутствующий Git, неверный Workspace/root, non-zero exit, большие stdout/stderr, одновременное заполнение обоих потоков, timeout, завершение дочерних процессов, ошибки Win32 API, отказ AssignProcessToJobObject до ResumeThread, reader exception, отмену зависшего чтения, cleanup handles, literal pathspec и отсутствие изменений репозитория.
- **REQ-09:** Изменения ограничены GitTool, его внутренним runner (если вынесен), связанными тестами и необходимым экспортом типов. Существующие инструменты и их контракты не регрессируют; в отчёте приведён полный diff и фактические результаты проверок.

## 6. Ограничения и правила

- До изменения кода изучить актуальные исходники и тесты; не считать описания в документации заменой проверки текущей реализации.
- Не создавать новые менеджеры, маршрутизаторы, реестры или абстракции сверх минимально необходимого внутреннего runner.
- Не менять ToolExecutor, ToolExecutorAdapter, Orchestrator, ApprovalManager, ExecutionRecorder, Workspace и ExecutionBackend в рамках этой задачи.
- Не ослаблять, не удалять и не переписывать существующие тесты ради прохождения.
- Не использовать `subprocess.Popen` как реализацию Windows runner: принятое решение 9.А требует прямой Win32 последовательности с suspended start и Job Object.
- Не возобновлять процесс до успешного `AssignProcessToJobObject`.
- Не использовать breakaway flags.
- Не использовать `CREATE_NEW_PROCESS_GROUP`, `taskkill` или завершение только главного процесса как замену Job Object.
- Не использовать `capture_output=True` с последующим усечением: ограничение памяти должно действовать во время чтения.
- Не запускать Git через shell и не принимать произвольные аргументы командной строки.
- Не выполнять никаких Git-команд, меняющих index, refs, worktree или конфигурацию.
- Не изменять пользовательские файлы/репозиторий в тестах; все интеграционные сценарии создавать во временных каталогах.
- Не расширять scope самостоятельно. При необходимости изменить существующий контракт, затронуть соседние модули, добавить зависимость или изменить согласованный дизайн — остановиться и запросить решение постановщика.
- Не заявлять о проверках, которые фактически не запускались.
- При обнаружении риска потери данных или невозможности гарантировать cleanup процесса остановиться и сообщить о блокере.

## 8. Тестирование и проверки

### Обязательные целевые сценарии

- [ ] Git отсутствует: понятная типизированная ошибка, процесс не запускается.
- [ ] Workspace не является экземпляром/валидным объектом Workspace либо путь не является корнем репозитория: корректная ошибка.
- [ ] Обычный Git-репозиторий и linked worktree: корень распознаётся корректно.
- [ ] status отражает staged, unstaged и untracked изменения; branch/head корректны для обычного состояния и detached HEAD.
- [ ] branches и log возвращают ограниченные и корректно разобранные результаты; некорректный лимит отклоняется до запуска процесса.
- [ ] diff и staged_diff различают рабочее дерево и index.
- [ ] changed_files корректно разбирает NUL-разделённые пути, включая пробелы, Unicode и символы, которые нельзя безопасно считать разделителями строк.
- [ ] При большом stdout и stderr память сохраняет не более соответствующего лимита для каждого потока; остаток вычитывается.
- [ ] stdout и stderr заполняются одновременно: процесс не зависает из-за чтения только одного pipe.
- [ ] Timeout вызывает TerminateJobObject и приводит к завершению потомка, удерживающего унаследованный pipe handle.
- [ ] Win32 порядок проверяется тестами: CreateJobObject/configure → CreateProcessW(CREATE_SUSPENDED) → AssignProcessToJobObject → ResumeThread.
- [ ] При ошибке AssignProcessToJobObject ResumeThread не вызывается; процесс/handles корректно завершаются и освобождаются.
- [ ] Проверяются ошибки CreateProcessW, CreateJobObject, SetInformationJobObject, AssignProcessToJobObject, ResumeThread, TerminateJobObject, WaitForSingleObject и reader.
- [ ] Зависший reader ограниченно отменяется через CancelSynchronousIo; cleanup не оставляет потоки/handles.
- [ ] Все handles закрываются при успешном запуске, timeout и каждой проверяемой ветке ошибки.
- [ ] Literal pathspec не интерпретирует строку вроде `:(glob)*.py` как Git pathspec magic; аргументы содержат `--literal-pathspecs` до подкоманды и `--` перед путями.
- [ ] Тест подтверждает, что GitTool не изменяет HEAD, index, tracked worktree и untracked files.
- [ ] Интеграционные тесты Windows запускаются на Windows 11 с установленным Git for Windows. Если окружение исполнителя не Windows, нельзя заявлять эти проверки пройденными; требуется согласовать способ их выполнения.

## 9. Критерии приёмки

- **AC-01 (REQ-01):** GitTool существует как самостоятельный компонент с типизированными результатами/ошибками и фиксированным read-only интерфейсом; ToolExecutor и Adapter не изменены и GitTool не зарегистрирован.
- **AC-02 (REQ-02):** Git обнаруживается через `shutil.which`; отсутствие Git, некорректный Workspace, отсутствие репозитория, несовпадение корня и non-zero exit проверяются тестами и дают явный неуспешный результат.
- **AC-03 (REQ-03):** Тесты подтверждают точный порядок Win32 запуска: процесс создан suspended, назначен в Job Object, только затем возобновлён; при ошибке назначения ResumeThread не вызывается.
- **AC-04 (REQ-04):** Тесты подтверждают параллельный drain stdout/stderr, ограничение сохраняемой памяти во время чтения, timeout через TerminateJobObject, ограниченное завершение reader-потоков и cleanup handles на успехе и ошибках.
- **AC-05 (REQ-05):** Набор разрешённых команд фиксирован; произвольные команды/args/shell невозможны. Для pathspec подтверждён literal mode; ни одна операция 9.Б не меняет репозиторий.

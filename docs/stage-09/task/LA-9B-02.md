# Задание LA-9B-02 — Исправление Windows runner и закрытие пробелов тестового покрытия GitTool

- **Базовая ветка и commit:** продолжение существующей ветки `stage-9b-git-tool`, исходное состояние `c7f514644b698d316366e9e2a2333840e882ecf2`. Перед началом сверить локальную ветку с `origin/stage-9b-git-tool`; не переключаться на новую ветку.

## 2. Контекст

Задача LA-9B-01 реализовала самостоятельный read-only GitTool и Windows runner. Отчёт `docs/stage-09/report/LA-9B-01.md` честно отмечает, что AC-02–AC-07 пока не подтверждены полностью из-за отсутствующих обязательных тестов.

При независимом чтении `src/local_agent/execution/tools/_windows_runner.py` обнаружена потенциально опасная ветвь cleanup: в обработчике исключения вызывается `check(TerminateProcess(...))`; если этот вызов или ожидание завершения выбрасывает исключение, выполнение может не дойти до `TerminateJobObject` и закрытия Job Object. Это способно оставить ресурсы/процессы незавершёнными. Также необходимо проверить устойчивость reader-потоков при ошибке чтения.

Эта задача является дополнением к LA-9B-01. Она не заменяет и не переписывает первоначальную реализацию. Продолжить работу в той же ветке `stage-9b-git-tool`; сохранить уже выполненные изменения и тесты. Отдельный PR для LA-9B-02 не создавать: после завершения LA-9B-01 и LA-9B-02 должен быть подготовлен один PR на подэтап 9.Б.

## 3. Цель и ожидаемый результат

Устранить обнаруженные риски cleanup Windows runner и добавить адресные тесты, которые подтверждают оставшиеся требования LA-9B-01 (AC-02–AC-07).

Результат:
- гарантированная попытка завершения Job Object и закрытия всех созданных handles при ошибках, без маскировки исходной ошибки;
- контролируемое поведение reader-потоков при ошибках и отмене чтения;
- тесты негативных ветвей Win32 API и точного порядка запуска процесса;
- интеграционные тесты GitTool для указанных ниже сценариев;
- обновлённый отчёт LA-9B-01 с фактическими доказательствами по каждому REQ/AC.

## 5. Требования

- **REQ-01:** Windows runner освобождает все созданные handles при успешном выполнении, timeout и ошибках на каждом этапе запуска/завершения. Ошибка TerminateProcess или ожидания не должна пропускать обязательную попытку TerminateJobObject/закрытия Job Object. Ошибки CloseHandle диагностируются; очистка остальных ресурсов продолжается.
- **REQ-02:** Ошибка reader-потока не оставляет stdout/stderr pipe без контролируемого drain/закрытия и не вызывает неограниченное ожидание процесса. Ошибка чтения и ошибка cleanup доступны вызывающему коду в диагностике.
- **REQ-03:** Тесты подтверждают порядок `CreateProcessW(CREATE_SUSPENDED) → AssignProcessToJobObject → ResumeThread`. При отказе AssignProcessToJobObject ResumeThread не вызывается, созданный процесс завершается, ресурсы освобождаются.
- **REQ-04:** Тестами проверяются значимые ошибки Win32 API (как минимум CreateJobObjectW, SetInformationJobObject, CreateProcessW, AssignProcessToJobObject, ResumeThread, TerminateJobObject, WaitForSingleObject, ReadFile и CloseHandle) и корректное продолжение cleanup после ошибки отдельного шага.
- **REQ-05:** GitTool корректно отклоняет неверный Workspace, путь Workspace, который не является корнем репозитория, отсутствие репозитория и несовпадение корня. Ошибки не маскируются под успешный результат.
- **REQ-06:** Все read-only операции используют literal pathspec. Интеграционный тест с именем, похожим на Git pathspec magic (например, `:(glob)*.py` как буквальное имя файла), подтверждает работу именно с буквальным путём. Снимки HEAD, index, tracked worktree и untracked файлов до/после read-only вызовов подтверждают отсутствие мутаций.
- **REQ-07:** Интеграционные тесты подтверждают корень linked worktree и корректность восьми операций в репозитории с detached HEAD, staged + unstaged + untracked изменениями одновременно, staged_diff, rename/copy (если формат операции поддерживает их различение), пробелами, Unicode и необычными символами в именах файлов. Если Git не представляет отдельный тип copy при используемых настройках, это ограничение должно быть объяснено, а не имитироваться.
- **REQ-08:** Отчёт LA-9B-01 обновлён: по каждому REQ-01–REQ-09 и AC-01–AC-09 указано фактическое состояние, ссылки на тесты и результаты. Явно указано, что тесты на Windows запускал пользователь, если именно он их запускал.

## 6. Ограничения и правила

- Сохранять текущие публичные API GitTool и ProcessResult, если нет доказанной необходимости менять их. При необходимости изменения публичного контракта остановиться и запросить согласование.
- Не использовать `subprocess.Popen` как замену принятому Win32 runner.
- Не вызывать ResumeThread до успешного AssignProcessToJobObject.
- Не полагаться только на `finally` без тестов, подтверждающих освобождение ресурсов при ошибках внутри cleanup.
- Не игнорировать ошибки TerminateJobObject/CloseHandle и не считать их успешным cleanup.
- Не завершать только главный процесс вместо Job Object, если процесс уже назначен в Job.
- Не ослаблять/удалять существующие тесты.
- Все Git integration tests выполнять во временных репозиториях. Не менять рабочий репозиторий пользователя.
- Не выполнять изменяющие Git-команды в реализации GitTool.
- Не заявлять о тестах/проверках, которые фактически не запускались. Отдельно указывать, кто запускал проверки.
- При обнаружении необходимости изменить scope, контракты или архитектуру остановиться и запросить постановщика.

## 8. Тестирование и проверки

### 8.1 Windows runner

- [ ] Успешная последовательность вызовов: Job Object создан и настроен; процесс создан suspended; назначен в Job; только затем ResumeThread.
- [ ] AssignProcessToJobObject возвращает ошибку: ResumeThread не вызван; процесс завершён; все handles закрыты.
- [ ] Ошибки CreateJobObjectW, SetInformationJobObject и CreateProcessW: все уже созданные handles закрываются.
- [ ] Ошибки ResumeThread, WaitForSingleObject и TerminateJobObject: cleanup продолжается; Job Object закрывается; потомки не остаются работать.
- [ ] Ошибка ReadFile в одном reader: второй поток и основной процесс не приводят к deadlock; результат содержит диагностику.
- [ ] Reader зависает: CancelSynchronousIo вызывается для нужного thread; ожидание ограничено; все handles закрываются.
- [ ] Ошибка CloseHandle одного ресурса не мешает попыткам закрыть остальные ресурсы и отражается в диагностике.
- [ ] Существующие проверки больших stdout/stderr, timeout и завершения дерева процессов продолжают проходить.

Тесты Win32 API могут использовать mock/fake на любой ОС, если это действительно тестирует runner logic. Windows integration tests должны оставаться отдельными и запускаться на Windows.

### 8.2 GitTool

- [ ] Неверный тип/состояние Workspace отклоняется до запуска Git.
- [ ] Workspace, не являющийся корнем репозитория, и каталог без Git-репозитория дают ожидаемую ошибку.
- [ ] Несовпадение `rev-parse --show-toplevel` с `Workspace.root` отклоняется.
- [ ] Linked worktree создаётся во временном каталоге и принимается как корректный репозиторий.
- [ ] Проверяются обычная ветка и detached HEAD.
- [ ] Одновременно существуют staged, unstaged и untracked изменения; status/changed_files отражают каждую категорию.
- [ ] diff и staged_diff возвращают разные ожидаемые данные.
- [ ] Проверяются имена с пробелами, Unicode, переводами строк/табуляцией (если файловая система и Git их поддерживают), а также буквальное имя `:(glob)*.py`.
- [ ] Rename/copy проверяются в пределах реально поддерживаемого формата вывода Git; ограничения Git detection документируются.
- [ ] До/после всех read-only операций сравниваются HEAD, содержимое index (например, `git ls-files --stage -z`), tracked worktree и untracked paths/content.

### 8.3 Контрольные команды

- [ ] Целевые тесты GitTool и runner.
- [ ] Windows integration tests на Windows 11 с Git for Windows.
- [ ] `uv run pytest -v`.
- [ ] `uv run ruff check .`.
- [ ] `git diff --check`.
- [ ] Проверка diff и списка файлов относительно актуальной `main`.

Если исполнитель не может запустить Windows integration tests на Windows, он обязан сообщить об этом и не отмечать соответствующие критерии пройденными.

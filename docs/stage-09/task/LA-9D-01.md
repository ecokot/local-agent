Навыки определяют поведение ролей; проектный план и эта постановка определяют конкретный контекст и требования.

## 2. Контекст

Подэтапы 9.Б–9.Г приняты и объединены в `main`. Текущая реализация содержит read-only GitTool, регистрацию фиксированных Git-действий в ToolExecutor, три изменяющие операции с двухфазным snapshot-bound approval и Windows runner на Job Object.

Подэтап 9.Д должен подтвердить согласованную работу этих частей на реальном временном локальном Git-репозитории, проверить прохождение Git-действий по исполнительной цепочке и закрепить фактические контракты и ограничения. Это завершающая проверка этапа 9, а не расширение возможностей Git.

Актуальный baseline подтверждён пользователем в локальной копии: ветка `main`, чистое рабочее дерево, `HEAD`, `origin/main` и удалённый `main` совпадают на `fa1765b7d1f3811b8c1874178aa2ca3930d4b4a4`.

Основные источники:
- `plan.MD`, разделы этапа 9 и подэтапа 9.Д;
- `docs/stage-09/report/LA-9A-01.md`, раздел 7;
- `MODULE_CONTRACTS.md`;
- `src/local_agent/execution/tools/git.py`;
- `src/local_agent/execution/tool_executor.py`;
- `src/local_agent/agents/tool_executor_adapter.py`;
- `src/local_agent/orchestrator.py`;
- `src/local_agent/execution/recorder.py`;
- `test/integration/test_git_mutations_windows.py`;
- `test/integration/test_git_tool_windows.py`;
- `test/test_tool_executor.py`;
- `test/test_tool_executor_adapter.py`;
- `test/test_orchestrator.py`.

В существующих тестах уже есть значительное покрытие реальных временных Git-репозиториев для branch/stage/commit, dirty и detached состояний, approvals, snapshot changes, restart/cancel, path validation, сохранности невыбранных файлов, hooks/filters, timeout и postconditions. Повторять эти проверки без конкретного пробела не нужно. До написания тестов исполнитель обязан сопоставить требования этой постановки с имеющимися сценариями и добавить только недостающие сквозные доказательства.

## 3. Цель и ожидаемый результат

Получить проверяемое подтверждение того, что GitTool:
1. работает с реальным временным локальным Git-репозиторием на поддерживаемой платформе Windows;
2. проходит через предусмотренную архитектурой исполнительную цепочку, не обходя ToolExecutor, ApprovalManager и ExecutionRecorder;
3. не выполняет изменяющие Git-операции без одобрения точного snapshot и сохраняет пользовательские изменения;
4. корректно отражает результаты и ошибки в существующей истории выполнения;
5. имеет документированные фактические контракты, ограничения и явно неподдерживаемые сценарии.

Результат — минимальный набор новых/уточнённых тестов, актуальная документация фактического поведения и отчёт LA-9D-01. Реализация принимается только по доказательствам, а не по самооценке исполнителя.

## 4. Объём работ

Разрешено и требуется:

- Сопоставить существующие Git unit/integration tests с REQ/AC этой постановки и зафиксировать, какие критерии уже покрыты без изменений.
- Добавить недостающие сквозные integration tests с реальным временным Git-репозиторием. Проверить как минимум успешное Git-действие через `ToolExecutorAdapter`; проверить Orchestrator-путь с реальным Git-действием, если текущие публичные интерфейсы позволяют собрать его без изменения архитектуры. Если такой тест требует изменения production wiring/контракта, остановиться и представить Planner конкретное доказательство и минимальный вариант; не расширять архитектуру самостоятельно.
- Проверить паузу и продолжение плана после approval для Git-действия: до approval mutating subprocess не вызывается; после approval выполняется ровно одобренное действие; ранее завершённые шаги не повторяются.
- Добавить сквозные проверки того, что отказ в approval и изменение snapshot после запроса approval не приводят к изменяющему Git-вызову и что фактический результат/ошибка действия доступен через ExecutionResult и ExecutionRecorder.
- Проверить в составе реальных репозиторных сценариев сохранность исходных staged, unstaged и untracked пользовательских данных. Использовать отдельные тестовые репозитории и явные assertions по содержимому файлов, index, HEAD и status.
- Проверить сценарии из утверждённого плана 9.Д, используя уже имеющиеся тесты там, где они достаточны: чистый репозиторий; пользовательские изменения; untracked/staged files; конфликт или смена HEAD/snapshot; отказ approval; commit с ограниченным набором файлов; Git недоступен; неверный/повреждённый workspace; повторный вызов после approval.
- Проверить журналирование Git-вызовов через существующий ExecutionRecorder: успешное выполнение, ожидаемая ошибка Git и отказ/ожидание approval. Проверять реальные поля/статусы существующего контракта, не вводить новый формат событий.
- Обновить `MODULE_CONTRACTS.md` в части фактического GitTool/ToolExecutor/Adapter/Recorder контракта и карты тестов, если проверка выявит устаревшие сведения. Указать, что реально реализовано, а что остаётся ограничением.
- Подготовить `docs/stage-09/report/LA-9D-01.md` по полному `REPORT_TEMPLATE.md`, сохранив все REQ/AC IDs и указав точные commits и исполнителей проверок.

Не входит в задачу:

- Новые Git-операции или расширение whitelist действий.
- Push, fetch, pull, merge, rebase, cherry-pick, tag, stash, reset, clean, restore, удаление веток и иные новые Git-возможности.
- Автоматический rollback, автоматическое восстановление файлов/index или попытки «починить» репозиторий после частичного сбоя.
- Новый менеджер, сервис, хранилище, журнал или слой маршрутизации.
- Переработка Orchestrator, ToolExecutorAdapter, ApprovalManager, ExecutionRecorder или архитектуры восстановления только ради более удобного теста.
- Полный restart recovery позиции ToolExecutorAdapter: текущая архитектура сохраняет approval и stage receipt в SQLite, но позиция Adapter хранится в памяти процесса. Это ограничение требуется отразить, а не устранять в 9.Д.
- Изменения `plan.MD` до отдельного решения после приёмки.
- Несвязанный рефакторинг, форматирование или изменения файлов вне обоснованного scope.
- Изменения production-кода, если требования можно доказать тестами и корректировкой документации.

## 5. Требования

- **REQ-01:** Исполнитель анализирует существующие GitTool unit/integration tests и тесты ToolExecutor, Adapter и Orchestrator; для каждого критерия AC указывает, какие существующие тесты уже дают доказательство и какие новые проверки необходимы. Дублирующие тесты без нового доказательства не добавляются.
- **REQ-02:** Реальный GitTool проходит хотя бы один сквозной сценарий через ToolExecutorAdapter на временном локальном Git-репозитории; тест проверяет реальный результат Git, а не только вызов FakeGitTool.
- **REQ-03:** Сквозной сценарий подтверждает, что mutating Git action до approval не запускает mutating subprocess, а после одобрения того же действия с теми же параметрами и неизменным snapshot выполняется. Уже завершённые шаги плана не выполняются повторно при resume.
- **REQ-04:** Сквозные сценарии подтверждают, что rejection и изменение snapshot после запроса approval не запускают соответствующий mutating Git subprocess; изменение snapshot приводит к новому запросу подтверждения в соответствии с существующим контрактом.
- **REQ-05:** На реальном временном репозитории доказано, что Git-операция с ограниченным набором путей не включает посторонние staged, unstaged или untracked изменения и не теряет их. Проверяются фактические файлы, HEAD, index и status.
- **REQ-06:** Для успеха и ошибки Git-действия ExecutionResult и ExecutionRecorder содержат фактический результат/статус/ошибку в рамках существующего контракта. Ожидание или отказ approval не должны ошибочно представляться как успешный запуск Git.
- **REQ-07:** Проверки 9.Д из `plan.MD` и раздела 7 `LA-9A-01` либо подтверждены существующими тестами, либо новыми тестами; непроверенные сценарии явно перечислены с причиной. Минимум: чистое/изменённое состояние репозитория, untracked/staged данные, отказ approval, изменение snapshot/HEAD, ограниченный commit, Git unavailable и неверный workspace.
- **REQ-08:** `MODULE_CONTRACTS.md` отражает фактический контракт GitTool и его интеграцию, включая список поддерживаемых операций, approval flow, журналирование и существенные ограничения. Не выдавать целевые или неподдерживаемые возможности за реализованные.
- **REQ-09:** Отчёт LA-9D-01 полностью соответствует текущему REPORT_TEMPLATE, отвечает по каждому REQ/AC, содержит полный список изменённых файлов, точные SHA проверенного кода и фактические результаты проверок с указанием, кто их запускал и в какой среде.
- **REQ-10:** Изменения ограничены разрешённым scope; существующие тесты не ослаблены и не удалены; публичные контракты и production behavior не изменены без предварительного согласования.

## 6. Ограничения и правила

### 6.1 Фиксированные решения

- Базовая ветка и commit — `main` / `fa1765b7d1f3811b8c1874178aa2ca3930d4b4a4`.
- Windows — обязательная целевая среда реальных Git integration tests, поскольку GitTool использует Windows runner. Тесты, требующие Windows, должны явно пропускаться на неподдерживаемой ОС с корректной причиной.
- Источник истины для выполнения — Python orchestration и существующие компоненты; модель не должна обходить ToolExecutor или самостоятельно выполнять Git.
- Все изменяющие Git-действия остаются ограниченными фиксированными action names и защищёнными существующим snapshot-bound approval.
- Пользовательские staged, unstaged и untracked изменения нельзя сбрасывать, перезаписывать, автоматически добавлять в commit или удалять.
- Нельзя выполнять автоматический stash/reset/clean/restore/rollback.
- Approval действия привязан к task/action/parameter hash; при изменении параметров или snapshot требуется новое подтверждение.
- SQLite остаётся источником истины для approval и execution state; JSONL не становится отдельным источником истины.
- Ограничение: per-repository lock синхронизирует потоки только внутри одного процесса; внешние процессы Git его не соблюдают.
- Ограничение: после timeout или postcondition failure автоматический rollback отсутствует.
- Ограничение: позиция ToolExecutorAdapter хранится в памяти; полное восстановление позиции после restart не реализовано, даже если approval и stage receipt переживают restart.
- `plan.MD` не менять в рамках этой задачи.

### 6.2 Делегированные решения

- Выбор точных тестовых функций/фикстур и размещение новых тестов в существующих test modules либо `test/integration/`.
- Способ создания и инициализации временных Git-репозиториев и вспомогательные локальные test helpers.
- Какие критерии подтверждаются существующими тестами, если их assertions непосредственно доказывают требуемое поведение.
- Небольшие исправления production-кода допускаются только если обнаружен воспроизводимый дефект, напрямую блокирующий REQ; до изменения исполнитель должен остановиться и получить решение Planner с указанием файла, поведения, минимального исправления и влияния на контракты.
- Техническая формулировка документации, не меняющая контракт.

### 6.3 Запрещённая работа

- Любое изменение фиксированных решений или публичных контрактов без согласования.
- Новые abstractions/managers/stores и общая перестройка тестовой архитектуры.
- Ослабление, удаление или перевод существующих тестов в skip ради прохождения.
- Изменения вне GitTool/его текущей интеграции, относящейся к требованиям, тестов и необходимой документации.
- Реальные Git-операции над рабочей копией проекта или иными пользовательскими репозиториями.
- Ручное редактирование `plan.MD`.

### 6.4 Git-полномочия для этой задачи

- **Разрешено без отдельного подтверждения:** читать репозиторий; создавать и коммитить изменения только в отдельной ветке `stage-9d-cross-cutting`; запускать тесты на временных тестовых репозиториях; публиковать эту feature branch и создать Draft PR в `main` после подготовки результата.
- **Требует отдельного разрешения:** merge PR; push/commit в `main`; force-push; изменение или удаление существующих веток; любые операции над пользовательскими локальными репозиториями.
- **Запрещено:** reset/clean/restore/stash с риском потери данных; переписывание истории; удаление пользовательских веток/файлов; Git-операции вне выделенной feature branch и временных тестовых репозиториев.
- **При сомнении:** остановиться и запросить постановщика.

### 6.5 Общие ограничения

- Изучить актуальные исходники и связанные тесты до изменения кода.
- Не дублировать существующую функциональность и не создавать новые менеджеры или уровни абстракции без обоснованной необходимости.
- Не менять публичные контракты и поведение за пределами задачи без отдельного согласования.
- Не расширять объём задачи самостоятельно.
- Не ослаблять и не удалять существующие тесты ради прохождения проверок.
- Не заявлять о выполнении команды или проверки, если она фактически не запускалась.
- При обнаружении противоречия, блокера или необходимости выйти за рамки задачи остановиться и запросить решение постановщика.
- Если Orchestrator-путь нельзя проверить без production изменений, представить Planner факты и не вносить эти изменения самостоятельно.

## 8. Тестирование и проверки

### 8.1 Кто запускает проверки

| Проверка / среда | Ответственный | Как передаётся результат |
|---|---|---|
| Целевые unit/integration tests в среде Developer | Project Developer | Точные команды, вывод и проверенный commit в отчёте |
| Полный pytest на Windows | Пользователь | Planner выдаёт команды; пользователь присылает полный фактический вывод |
| Ruff и diff check на Windows | Пользователь | Planner выдаёт команды; пользователь присылает фактический вывод |
| GitHub PR checks / CI | CI, если настроен для репозитория | Ссылка на workflow/run; если CI отсутствует, прямо указать «не настроен/не запускался» |

### 8.2 Обязательные проверки

- [ ] Целевые тесты новых/изменённых сценариев, включая integration tests с реальным временным Git-репозиторием на Windows.
- [ ] Существующие тесты GitTool: `test/test_git_tool.py`, `test/integration/test_git_tool_windows.py`, `test/integration/test_git_mutations_windows.py`.
- [ ] Существующие тесты исполнительной цепочки: `test/test_tool_executor.py`, `test/test_tool_executor_adapter.py`, `test/test_orchestrator.py`.
- [ ] Полный `uv run pytest -v` на Windows пользователя.
- [ ] `uv run ruff check .` на Windows пользователя.
- [ ] `git diff --check origin/main...HEAD` на Windows пользователя.
- [ ] Проверка полного списка файлов и diff относительно baseline; отсутствие изменений вне scope.
- [ ] Проверка отчёта по полному `docs/templates/REPORT_TEMPLATE.md`, соответствия отчёта PR HEAD и наличия доказательств по каждому REQ/AC.

Новые тесты должны использовать реальные временные Git-репозитории там, где проверяется Git state/side effect. FakeGitTool допустим для unit-контрактов, но не заменяет real-Git integration evidence. Не требуется повторно добавлять отдельный тест для каждого уже покрытого низкоуровневого failure mode.

## 9. Критерии приёмки

- **AC-01 (REQ-01):** В отчёте есть карта REQ/AC → существующие и новые тесты; повторное покрытие без нового доказательства не добавлено.
- **AC-02 (REQ-02):** Есть успешный integration test реального GitTool через ToolExecutorAdapter на временном репозитории; результат проверяется по Git state. Orchestrator-путь проверен, если он доступен через существующие интерфейсы без изменения архитектуры; иначе предоставлено конкретное техническое обоснование и тест Adapter остаётся обязательным.
- **AC-03 (REQ-03):** Тест доказывает отсутствие mutating subprocess до approval, успешное выполнение после approval и отсутствие повторного выполнения завершённых шагов при resume.
- **AC-04 (REQ-04):** Тесты доказывают, что rejection и изменившийся snapshot не приводят к mutating Git-вызову; для изменившегося snapshot фиксируется новый pending approval.
- **AC-05 (REQ-05):** Тесты проверяют сохранность посторонних staged/unstaged/untracked данных по реальному содержимому, index, HEAD и status; в commit попадают только явно подтверждённые пути.

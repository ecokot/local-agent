
# ExecutionBackend

## Назначение

`ExecutionBackend` — самостоятельный компонент выполнения команд в изолированных Docker-контейнерах.

Он отвечает за:
- запуск Docker-контейнера для каждой команды;
- передачу команды без использования системной оболочки;
- предоставление контейнеру доступа к Workspace;
- применение ограничений контейнера;
- получение stdout, stderr и кода завершения;
- обработку тайм-аута;
- удаление контейнера после выполнения;
- проверку фактического удаления контейнера.

Backend не отвечает за пользовательские разрешения, подтверждения действий, планирование задач или запись истории выполнения инструментов.

## Публичный API

Пакет `local_agent.execution` экспортирует:

- `ExecutionBackend`
- `ExecutionResult`
- `ExecutionBackendError`

### Создание Backend

```python
backend = ExecutionBackend(
    workspace=workspace,
    image="local-agent-python-test:3.12",
    timeout_seconds=60,
)
```

Параметры:

| Параметр | Назначение |
|---|---|
| `workspace` | Экземпляр `Workspace` |
| `image` | Имя локального Docker-образа |
| `timeout_seconds` | Максимальное время выполнения команды |

Значения по умолчанию:
- образ: `local-agent-python-test:3.12`;
- тайм-аут: 60 секунд.

Backend требует экземпляр `Workspace`, непустое имя образа и конечное положительное значение тайм-аута.

Docker запускается через CLI с запретом автоматической загрузки образа (`--pull=never`).

## Выполнение команды

```python
result = backend.execute([
    "python",
    "-c",
    "print('Hello')",
])
```

Команда передаётся как последовательность строковых аргументов. Системная оболочка не используется.

Строка, bytes, пустая последовательность, нестроковые аргументы, пустой исполняемый файл и аргументы с нулевым байтом отклоняются.

Путь Workspace, содержащий запятую, не поддерживается из-за формата Docker bind mount.

## Результат выполнения

`ExecutionResult` — неизменяемый dataclass:

| Поле | Тип | Назначение |
|---|---|---|
| `stdout` | `str` | Стандартный вывод |
| `stderr` | `str` | Поток ошибок |
| `exit_code` | `int \| None` | Код завершения |
| `timed_out` | `bool` | Признак превышения тайм-аута |

При обычном завершении `exit_code` содержит код завершения Docker CLI.

При тайм-ауте:
- `timed_out` равен `True`;
- `exit_code` равен `None`;
- Backend пытается принудительно удалить контейнер;
- затем ожидает завершения Docker CLI;
- если Docker CLI не завершается в течение времени очистки, процесс принудительно завершается.

## Ограничения Docker-контейнера

Для каждого выполнения создаётся отдельный контейнер со случайным именем.

Backend применяет следующие ограничения:

| Параметр | Значение |
|---|---|
| Сеть | `--network none` |
| Память | `512m` |
| CPU | `1` |
| Количество процессов | `64` |
| Linux capabilities | `--cap-drop ALL` |
| Дополнительная защита | `no-new-privileges` |
| Пользователь | `10000:10000` |
| Рабочий каталог | `/workspace` |
| Доступ к файлам | Только bind mount Workspace |

В контейнер монтируется Workspace хоста в `/workspace`.

Команда выполняется из `/workspace`.

Другие каталоги хоста Backend не монтирует.

## Жизненный цикл контейнера

1. Backend формирует команду Docker.
2. Создаёт отдельный контейнер.
3. Передаёт команду на выполнение.
4. Получает stdout и stderr.
5. Проверяет наличие контейнера через `docker inspect`.
6. Удаляет контейнер через `docker rm -f`.
7. Проверяет отсутствие контейнера повторным `docker inspect`.
8. Возвращает `ExecutionResult`.

При тайм-ауте удаление контейнера выполняется до завершения ожидания Docker CLI.

## Ошибки

`ExecutionBackendError` возникает при ошибках запуска Docker CLI, проверки состояния контейнера или его удаления.

Ошибки некорректных входных параметров представлены `TypeError` или `ValueError`.

## Границы ответственности

`ExecutionBackend`:
- выполняет команды в Docker;
- изолирует выполнение настройками контейнера;
- управляет временем выполнения и очисткой.

`Workspace`:
- определяет рабочую область проекта.

`ToolExecutor`:
- отвечает за разрешения и подтверждения;
- управляет выполнением инструментов;
- взаимодействует с `ExecutionRecorder`.

Backend не заменяет эти компоненты и не реализует их обязанности.

## Ограничения и безопасность

Docker-изоляция снижает риск воздействия выполняемого кода на хост, но сама по себе не является доказательством абсолютной безопасности.

Проверки фактической конфигурации Docker, доступа к файлам хоста, сетевой изоляции, capabilities и других ограничений зафиксированы в `docs/EXECUTION_ISOLATION_RESEARCH.md`.

Интеграция Backend с `RunCommandTool` и `RunTestsTool` выполняется отдельно и не входит в текущую реализацию самостоятельного Backend.
